# multi_agent

## 역할
- 이 폴더: D5 멀티 에이전트를 둡니다. Supervisor(LLM 1번)가 질문을 보고 다음 길 하나(RAG 에이전트 · 대체 부품 에이전트 · 끝내기 · 가격 안내 · 거절)를 고르고, 고른 에이전트가 질문 전체를 답한 뒤 답 검사(코드)를 지나 끝나는 구조입니다(11-09, 강의 IV-3 15강).
- 넣는 것: Supervisor 지시서의 형식 · 이유 코드 · 상한(`contracts.py`), 멀티용 상태, Supervisor(지시서 · 답 검사), 에이전트 노드(`agents/`), 조립.
- 넣지 않는 것: D4 단일 에이전트 그래프(`backend/graph/`, D5 비교의 기준선. 11-06 강사 검토 뒤 D4 v2로 고쳤고 지금도 단일 에이전트 기준선입니다), 숫자 · 단위 비교(`backend/judge/`), 검색 구현(`backend/rag/`), LLM 직접 호출([services](../services/SERVICES.md)의 `llm.py`만 씁니다), 프롬프트 원문(`backend/prompts/`), 도구 정의(`backend/mcp_skill/`).
- 담당: 에이전트

## 왜 `graph/`와 따로 두었나 [결정 11-05 정운]
- **비교 기준선 보호:** 가이드는 D4 단일 그래프로 기준 점수를 재고 D5에 멀티로 나눠 같은 평가셋으로 비교하라고 합니다. 단일 코드가 같은 폴더에서 바뀌면 기준선이 흔들립니다. 폴더가 다르면 단일은 그대로 남습니다.
- **갈아엎을 코드와 고정 코드의 분리:** 멀티는 설계를 하면서 자주 바뀝니다. 기준선은 바뀌면 안 됩니다. 둘이 섞이면 어느 쪽이 바뀌었는지 가려내기 어렵습니다.
- **정리가 쉬움:** 멀티가 자리 잡으면 단일 폴더만 "기준선 보관"으로 표시하거나 치우면 됩니다.
- 11-06: 강사 검토("범위 판정을 첫 단에서 먼저", "단순 직렬 흐름")를 받아 D4를 D4 v2로 고쳤습니다(사실 확인 → 7가지 라우팅 → 질문 종류별 길, 11-06 뒤 가격을 더해 8가지, 판정 · 찾기는 이 폴더의 대체 부품 에이전트 코드). D4 v2도 단일 에이전트 기준선이며 폴더는 그대로 나눠 둡니다. D4 v1 점수는 D4 v2 점수가 아닙니다.
- `SOJAFIT.md` 트리는 원래 `graph/`를 Supervisor 자리로 적었으나, 위 이유로 새 폴더를 만들고 이 문서와 트리 · 담당 표에 함께 적었습니다(AGENTS.md 규칙 9, `SOJAFIT.md` "파일을 만들거나 옮길 때" 1번).

## 의존 방향
- `multi_agent`는 `graph`를 불러 쓸 수 있습니다. 처음에는 단일의 검색 · 채점 · 재작성 함수를 그대로 감싸고, 하나씩 새 로직으로 바꿉니다.
- D4 v2(11-06)부터 `graph`도 이 폴더의 사실 확인(`facts.py`) · 판정 노드 두 개(`agents/judge.py`의 `judge_read_agent` · `judge_agent`) · 거절 문구 · 가격 안내 문구와 판정 답 틀(`messages.py`) · 질문 종류와 이유 코드(`contracts.py`) · `Facts`와 사실 글(`supervisor.render_facts`)을 불러 씁니다. D4 v2와 D5가 같은 사실 · 같은 판정 코드로 비교되게 하려는 것입니다. Supervisor 판단과 조립(`build.py`)은 `graph`가 부르지 않습니다.
- `multi_agent`는 `judge` · `rag` · `services`를 불러 씁니다. 판정의 숫자 비교는 `judge`에서만 합니다(AGENTS.md 규칙 7).

## 구조 결정
- 11-09 재구성 [결정 11-09 정운]: 강사 피드백("Supervisor가 에이전트 앞뒤에 있어 헷갈린다", LLM 단계가 많아 p95 19초 · 50문항 1.10달러)과 강의 패턴(IV-3 15강 cell 14: Supervisor가 하나를 고르고 그 에이전트가 답하면 끝, IV-2 18 · 20강: 고리는 조건부 간선, 03강: 갈림길은 간선 표, 09강: 인터럽트)을 따릅니다.
  - 그래프: `START → 입력 읽기 → 품번·판 확인 → Supervisor`. Supervisor가 `RAG 에이전트` · `대체 부품 에이전트` · `가격 안내` · `거절` · `끝내기`(일상 대화) 중 하나로 갑니다. 갈림 함수는 갈 노드 이름을 돌려주고 간선 표 키도 노드 이름이라(강의 20강) 그림 간선에 영어 라벨이 없습니다(지시서의 `next` 영어 이름 → 노드 이름은 `supervisor.ROUTES`). 두 에이전트 → `답 검사` → `끝내기` | `거절`, `끝내기` · `거절` · `가격 안내` → END.
  - Supervisor(Sonnet 1번): 범위 판정 · 질문 종류 · 다음 길 하나와 그 에이전트의 지시(`task`: 목표 · 출력 · 경계 · 첫 검색어 · 묘사한 정격), 여러 개를 묻는 질문에서 거절하는 부분(`declined`). 형식이 틀리면 `llm.chat`이 다시 부르고 끝내 틀리면 거절합니다. 대체 부품 에이전트가 꺼져 있으면 RAG 에이전트로 돌립니다.
  - RAG 에이전트(하위 그래프, Haiku 1~2번): `검색` → `근거 채점·답 쓰기` → 근거가 없으면(다른 검색어가 있거나 품번 필터 안 0건) `검색`으로 되돌아가는 조건부 간선, 검색은 `MAX_SEARCHES`(2)바퀴까지. 인용 검사(코드)를 지난 답이나 거절 사유(not_found · verify_failed · search_error)를 냅니다. 여러 개를 묻는 질문은 근거가 있는 부분만 답합니다(partial).
  - 대체 부품 에이전트(하위 그래프, Haiku 1번): `회로 역할 읽기` → `대체 부품 판정`(코퍼스 밖 요구 관문 · 빠진 값 1번 묻기(인터럽트) · 사양 표 조회 · 조건별 비교(코드) · 코드 답 틀). 재개하면 판정 노드부터 다시 돌아 읽기 LLM을 다시 부르지 않습니다. 인터럽트를 따로 `사람 확인` 노드로 나누지는 않았습니다.
  - 답 만들기: 두 에이전트가 나갈 때 답을 완성합니다(RAG 답 · 판정 답 틀 + 거절한 부분 한 줄씩, `messages.with_declined`). 실패면 답 없이 거절 사유를 냅니다.
  - 답 검사(코드): 인용 번호가 에이전트가 받은 근거 안인지, 근거 인용이 하나라도 있는지(판정 답 틀은 표 인용이라 제외) 봅니다. 걸리면 거절합니다. 예전 숫자 검사는 종합(LLM) 글의 숫자를 보던 것이라 종합이 없어지며 대상이 없어 뺐습니다.
  - 뺀 것: Send로 할 일 1~3개 동시 실행, 모으기(`collect`) · 답 정리(`single`) · 종합(`synth`, Sonnet) 노드, 재계획 고리(`MAX_REPLANS`), 할 일 보고서(`TaskReport`). 품번 없이 사양만 준 질문을 찾기 → 재계획 → 그 품번 문서 검색으로 잇던 길도 없어졌고, RAG 에이전트의 정격 품번 찾기(`find_parts_by_specs`)만 남습니다.
- 상한(질문당): Supervisor LLM 1번, RAG 검색 2바퀴(LLM 2번), 대체 부품 읽기 1번(`LAB_READ_VOTES`로 늘릴 수 있음) · 인터럽트 1번. 넘으면 고리를 나가 거절합니다(AGENTS 규칙 6).
- 예전 구조(기록): 11-05 허브 구조(Supervisor가 서브에이전트가 끝날 때마다 판단, 질문당 판단 4번 · 멀티 비용의 96%가 Supervisor) → 11-06 계획형(계획 → Send 동시 실행 → 모으기 → 정리 · 종합 → 답 검사) → 11-07 실패 고리(모으기 → 재계획 1번). 그림은 참조/아티팩트 "SojaFit 멀티 에이전트 구조" v1 · v2입니다.
- 11-05 결정 중 그대로인 것: 도구는 MCP 서버(stdio) 한 곳에 모읍니다. 거절 이유는 내부 코드로 Langfuse에 남기고 사용자에게는 일상어로 보여 줍니다.

## 파일
- `MULTI_AGENT.md` — 이 문서
- `__init__.py` — 패키지 표시
- `state.py` — 멀티용 공용 메모장 `MultiState`와 두 에이전트 하위 그래프의 받는 칸(`RagIn` · `JudgeIn`) · 안 칸(`RagState` · `JudgeState`) · 돌려주는 칸(`RagOut` · `JudgeOut`). 받는 칸에 `path`를 넣지 않아 경로가 두 번 쌓이지 않는다. 지나간 노드 이름(`path`)은 단일 그래프와 같은 말(거절 등)을 써서 평가 채점기가 읽을 수 있게 한다
- `facts.py` — 질문의 품번 · 개정판이 코퍼스 목록에 있는지 확인해 `Facts`를 만든다(`make_facts`). 목록은 호출하는 쪽이 넘기거나(`make_facts`), MCP 도구 `check_corpus`로 묻는다(`make_lookup`, 주문 코드가 붙은 품번 `1N4148 R0G`는 앞 기본 품번이 있으면 있음). 그래프 노드 `facts_node`(멀티의 `품번·판 확인`)는 `lookup` 없이 쓰면 비워 둔다
- `messages.py` — 거절 사유를 사용자 일상어 문구로 바꾼다(`refusal_message`. 사실 확인 결과의 없는 품번 · 개정판을 넣는 `refusal_for`는 D4 v2 거절 노드도 쓴다). 가격 · 재고 질문에는 값 없이 화면이 따로 보여 준다는 안내를 만든다(`price_message`). 판정 결과를 코드 틀 답으로 만든다(`render_judgement`). Supervisor가 거절한 부분을 답 끝에 붙인다(`with_declined`)
- `build.py` — 조립. 입력 읽기 → 품번·판 확인 → Supervisor → (RAG 에이전트 | 대체 부품 에이전트, 하위 그래프) → 답 검사 → 끝내기 · 거절, Supervisor에서 바로 끝내기 · 가격 안내 · 거절. 갈림길은 간선 표로 적는다. 대체 부품 에이전트는 사양 표 도구(`specs` · `find`)와 체크포인터가 있어야 켠다. 웹을 켜려 하면 거부
- `agents/` — 에이전트 노드(폴더 설명은 이 문서에 적는다): `docs.py` RAG 에이전트 노드(`search_step` 검색: 지시서 검색어 · 품번 필터 · 정격으로 품번 찾기 · 다른 품번 줄 거르기 · 변형 품번 주석, `answer_step` 근거 채점·답 쓰기: LLM 1번 + 인용 검사 + 답 · 거절 사유 · 다음 검색어, `after_answer` 고리 갈림길: '검색' 또는 END), `judge.py` 대체 부품 에이전트(읽기 노드 `judge_read_agent`: 역할 · 회로 값을 LLM 1번으로 읽음, 판정 노드 `judge_agent`: 코퍼스 밖 요구면 거절 사유로 보고(SPEC 8.3)하고, 아니면 빠진 값을 인터럽트로 한 번 묻고 사양 표 값으로 `backend/judge/verdict.py`가 판정. 멀티는 `judge_task_node`가 판정 결과를 답 틀의 답으로, 실패를 거절 사유로 바꾼다), `__init__.py` 패키지 표시
- `supervisor.py` — Supervisor. `plan_node`(지시서 LLM, 형식 실패면 거절, 대체 부품이 꺼지면 RAG로) · `after_plan`(지시서의 다음 길을 갈 노드 이름으로, `ROUTES`), 답 검사 `check_node`(인용) · `after_check`. 확인된 사실 `Facts`와 사실 글 `render_facts`는 D4 v2 라우팅도 같은 글로 받는다. LLM은 `chat` 함수로 받아 시험에서 가짜로 바꾼다
- `contracts.py` — Supervisor 지시서 `Plan`(질문 종류 8가지, 다음 길 docs · judge · finish · price · refuse, 거절이면 거절 사유 필수, 에이전트를 고르면 지시 필수, 대체 부품은 후보 판정 · 찾기만)과 에이전트 지시 `Task`(목표 · 출력 · 경계 · 첫 검색어 · 묘사한 정격), 거절한 부분 `Declined`, 판정 코드의 짧은 보고 `AgentReport`, 이유 코드 `Reason`(거절 7종 · 재시도 3종), 검색 상한
