## 결정
- 기준 평가셋을 v3로 새로 만든다. `evals/dataset_v1.jsonl` · `evals/dataset_v2.jsonl`은 파일과 해시(`evals/FROZEN.json`)를 그대로 두고, 지금까지의 측정(#31 ~ #42) 기록으로만 쓴다. v3를 동결한 뒤의 개선 전후 비교는 v3로 잰다.
- v3에는 판정 분야(후보 판정 · 후보 찾기) 문항을 늘리고, 후보 판정 문항마다 판정 5종 중 정답 판정을 적는다.
- 청킹부터 다시 잰다. 순서는 청킹 결함 고침 → 다시 임베딩 · 적재(먼저 로컬 DB) → 검색 지표(dev 세트) → 에이전트 측정(v3)이다. test 세트는 마지막 확인에만 쓴다. 운영 DB 재적재는 따로 승인한다.
  - 알려진 청킹 결함: 표가 든 조각을 건너뛸 때 같은 제목 아래 주석(측정 조건, 같은 부품이라는 주석)까지 버린다(`backend/rag/pipeline/chunk.py`).
- 목표 지표(11-06 중간 점검 최소 기준):
  - 응답 시간: 질문 1건 p95 10초 이내. 그래프에 들어가서 끝날 때까지 재고, 사람 확인(interrupt)을 기다리는 시간은 뺀다.
  - 검색: 문서 단위와 페이지 단위 모두 Recall@5 0.95 이상, MRR 0.95 이상.
  - 판정: 후보 판정 문항에서 판정 5종이 정답과 같은 비율을 보고한다. 목표 수치는 정할 것.
- 부품 사양 표([ADR 0013](0013-부품-사양-표는-13종을-규칙으로-만들고-애매한-값은-뺀다.md))는 그대로 둔다.

## 이유
- v2 70문항은 모두 한 가지만 묻고 끝나는 질문이고, 후보 판정은 9문항뿐이다. 그래서 판정 개선과 여러 일을 엮는 질문의 차이가 드러나지 않았다. 같은 판정 길 코드(a420a7a)에서 단일(#41 S9)과 멀티(#42)의 정답 근거로 답함 + 올바르게 거절함은 54 · 56 대 56 · 56으로 같았다.
- v2 파일을 고치면 지금까지의 측정과 비교할 수 없고, 동결 평가셋을 고치지 않는다는 규칙(AGENTS.md 지킬 것 1)을 어긴다. 그래서 새 파일로 만든다.
- 평가셋 정답 위치는 청크 번호가 아니라 (PDF, 페이지)로 적혀 있다(`evals/runners/run_retrieval.py`의 `gold_locations`). 청크를 다시 잘라도 정답을 다시 쓰지 않아도 된다.
- 지금 값은 목표와 멀다.
  - 응답 시간 p95(실행기 정의, 70문항 중 `int(0.95 × 70)`번째): 단일(#41 S9) 30.9 · 29.3초, 멀티(#42) 35.3 · 37.9초.
  - Page Recall@5: dev 세트 46문항 0.859(#26, 11-04).
  - 문서 Recall@5 · MRR: 서비스 경로 v1 관련 19문항에서 1.000 · 1.000(11-03)이지만, 문항이 적다.
- 부품 사양 표: 사양 표가 청킹이 값을 못 뽑아서 생긴 우회책이 아닌지 점검했다. 아래 두 가지 때문에 청킹 문제로 보지 않는다.
  - 표 행 청크에는 문서 · 페이지 · 표 제목 · 품번별 값이 들어 있다. 예: `1N5817 SERIES_H2104.pdf` 1페이지 VRRM 행의 `1N5817: 20 | 1N5818: 30 | 1N5819: 40 | UNIT: V`.
  - 사양 표는 숫자 비교와 품번 9,589개의 후보 찾기를 코드로 하려고 그 값을 미리 뽑아 둔 것이다. 행마다 값이 나온 청크와 페이지를 가리킨다.
