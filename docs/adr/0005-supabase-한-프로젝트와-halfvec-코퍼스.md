# 0005 Supabase 프로젝트 하나에 서비스와 코퍼스를 두고, 코퍼스 벡터는 halfvec으로 저장한다

- 날짜: 2026-11-02
- 상태: 채택
- 근거: 조장 하정운 결정(11-02), 로컬 compose DB 실측(11-02), Supabase 대시보드(11-02), `backend/rag/retrieve.py`의 `_dense`

## 결정
- 서비스 표와 코퍼스를 Supabase 프로젝트 하나(무료, DB 500MB)에 둔다. 용량 때문에 코퍼스를 줄이지 않는다.
- 코퍼스 벡터는 `halfvec`으로 저장하고, Supabase에는 HNSW 인덱스를 만들지 않는다. 전환은 임베딩 모델을 확정하고([ADR 0004](0004-임베딩-1536차원은-임시-결정.md)) 같은 코퍼스·동결 평가셋에서 Recall@5·MRR이 떨어지지 않는 것을 확인한 뒤에 한다. 그 전까지 기본은 `vector`(`RAG_VECTOR_TYPE=vector`)이고, 전환은 `db/manual/halfvec.sql.manual`로 한다.
- DB가 400MB를 넘으면 벡터 표(`chunk_embeddings`)만 새 무료 프로젝트로 옮기는 안을 먼저 검토한다. 청크 글과 문서 목록은 업무 표 외래키가 물고 있어 서비스 프로젝트에 둔다. 이 분리는 미확정 대안이다. 지금 `retrieve.py`는 `DATABASE_URL` 연결 하나로 dense 검색과 본문 조회를 하므로, 나누기 전에 연결 주소, 두 DB의 chunk id 대응, 검색·본문 조회 경로, 벡터 DB 장애 처리, 전환 검증 조건을 정하고 검증한다.
- 평가 실행은 Supabase에 체크포인트를 쓰지 않는다. 서비스 대화의 체크포인트는 재개와 이어 하기에 쓰므로 지우지 않는다.

## 이유
- 로컬 실측(문서 1,360건, 청크 52,244개, MiB 기준): 코퍼스 합계는 지금 829.5MiB, HNSW만 빼면 466.7MiB, `halfvec`에 HNSW 없이 258.0MiB, 같은 본문 벡터를 한 번만 두면 237.8MiB다.
- 지금 벡터 52,244개는 `halfvec`으로 바꿔도 값이 같다(`embedding::halfvec::vector = embedding` 52,244/52,244). 청크 1,000개를 질의로 쓴 정확 검색 top-5는 집합이 100% 같았고 순서는 999/1000 같았다(다른 1건은 거리 차 6.6e-8).
- 정확 검색 시간(로컬 Docker, 질의 30개 중앙값)은 float32 230.5ms, `halfvec` 140.2ms, 본문 중복 제거 119.6ms다. Supabase 무료 서버 시간은 재지 않았다.
- `retrieve()`는 HNSW가 한국어 질문에서 가까운 청크를 놓쳐(11-01) 인덱스를 끄고 정확 검색한다. 11-02에도 `halfvec` HNSW는 질의 30개 중 4개에서 정확 검색 top-5 청크를 놓쳤다.
- 대시보드 사용량은 26MB였고, 무료 유예 기간이 끝나 한도를 넘으면 프로젝트가 요청을 받지 못한다. 서비스 데이터는 그래프가 없어 추정만 있다(대화 1건 체크포인트 약 90~250KB). 평가 실행(50문항 × 20회)을 같은 DB에 쓰면 134~321MB로 혼자 한도를 위협한다.
