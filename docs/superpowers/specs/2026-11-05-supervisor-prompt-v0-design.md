# Supervisor Prompt V0 설계

상태: 사용자 검토 대기

작성일: 2026-11-05

## 1. 목적

Supervisor Prompt V0는 SojaFit의 수퍼바이저 후보 세 모델이 사용자 요청과 현재 실행 상태를 읽고, 다음 실행 경로를 동일한 구조로 결정하도록 만드는 비교용 기준선이다.

V0의 성공 기준은 최종 사용자 답변의 품질이 아니다. 다음 네 값을 정확하고 일관되게 반환하는지가 범위다.

- 질문 유형(`question_type`)
- 답변에 필요한 근거 종류(`required_evidence`)
- 현재 상태에서 실행할 다음 경로(`next_action`)
- 질문 유형에 대응하는 사유 코드(`reason_code`)

프롬프트는 특정 모델의 전용 문법에 의존하지 않는 명시적 규칙형으로 작성한다. 세 후보 모델에는 같은 프롬프트, 입력 표현, 출력 스키마와 테스트 사례를 적용한다.

## 2. 범위

### 포함

- Supervisor 전용 시스템 프롬프트 V0
- 사용자 요청의 여섯 유형 분류
- 필요한 근거 종류 선택
- 현재 실행 상태에 따른 다음 경로 선택
- 네 필드 구조화 출력
- 세 후보 모델의 동일 조건 비교
- 정상 요청 기준선 평가

### 제외

- 서브 에이전트 프롬프트 작성
- Supervisor가 부품 사양을 직접 분석하거나 대체 가능성을 판정하는 일
- Supervisor가 사용자용 최종 답변을 작성하는 일
- 임베딩, 검색기, reranker 또는 판정 모델 재선정
- 프롬프트 인젝션 방어 규칙과 공격 평가셋
- 최종 운영 아키텍처 확정

프롬프트 인젝션 방어는 정상 동작 기준선을 확보한 다음 별도 단계에서 설계한다. 다만 V0 입력은 이후 방어 규칙을 추가할 수 있도록 사용자 요청, 현재 상태, 외부 자료의 경계를 분리한다.

## 3. Supervisor 책임

Supervisor는 다음을 수행한다.

1. 사용자의 원래 요청을 분류한다.
2. 현재까지 완료된 작업과 확보된 근거를 확인한다.
3. 답변에 필요한 전체 근거 종류를 선택한다.
4. 현재 상태에서 실행할 다음 경로 하나를 선택한다.
5. 정해진 네 필드만 구조화하여 반환한다.

Supervisor는 다음을 수행하지 않는다.

- 검색, 회로 분석 또는 수치·단위 비교를 직접 수행하지 않는다.
- 입력과 상태에 없는 품번, 수치, 극성 또는 조건을 추측하지 않는다.
- 대체 가능 여부를 직접 판정하지 않는다.
- 사용자에게 보여 줄 최종 문장을 작성하지 않는다.
- 서브 에이전트가 반환한 근거를 확보되지 않은 다른 근거로 확대 해석하지 않는다.

`judge_answer_agent`가 근거를 이용해 판정과 사용자용 답변을 작성한다. Supervisor는 분류, 근거 요구사항 선택, 라우팅과 결과 전달을 담당한다. 이 역할 분담은 V0가 따르는 현재 계약이며 최종 아키텍처 확정을 의미하지 않는다.

## 4. 입력 계약

Supervisor 입력은 개념적으로 다음 세 영역으로 분리한다.

```text
[사용자 요청]
사용자가 처음 입력한 원문

[현재 상태]
- 완료된 작업
- 확보된 근거 종류
- 직전 실행 결과
- 실패 또는 부족 정보

[외부 자료]
검색 문서 또는 서브 에이전트가 반환한 내용
```

최초 호출에서는 현재 상태와 외부 자료가 비어 있을 수 있다. 중간 서브 에이전트가 실행된 뒤에는 그 결과를 현재 상태와 외부 자료에 추가하고 Supervisor를 다시 호출할 수 있다.

기존 동결 70문항처럼 사용자 입력만 있는 평가에서는 빈 현재 상태와 빈 외부 자료를 사용한다. Gold label, 기대 답, 채점 이유와 정답 청크는 모델 입력에 포함하지 않는다.

## 5. 질문 유형

`question_type`은 다음 여섯 값 중 하나다.

| 값 | 정의 |
|---|---|
| `out_of_scope` | 다이오드 교체, 회로 역할 또는 정격 확인과 무관한 요청 |
| `insufficient_information` | 범위 안이지만 대상 또는 질문 목적이 부족하여 안전한 다음 작업을 정할 수 없는 요청 |
| `candidate_judge` | 특정 후보 품번을 대상 위치에 사용할 수 있는지 묻는 요청 |
| `candidate_find` | 대체 후보를 요청하지만 후보 품번은 제시하지 않은 요청 |
| `role` | 대상 다이오드의 회로 내 역할, 연결 또는 전류 경로를 묻는 요청 |
| `rating` | 특정 다이오드의 정격, 특성, 시험 조건, 패키지 또는 개정판을 묻는 요청 |

### 분류 우선순위

하나의 요청에 여러 의도가 있으면 다음 순서로 처음 만족하는 유형을 고른다.

1. `out_of_scope`
2. `insufficient_information`
3. `candidate_judge`
4. `candidate_find`
5. `role`
6. `rating`

교체 의도와 단순 사양 확인이 함께 있으면 교체 의도를 우선한다. 예를 들어 특정 후보의 정격과 실제 대체 가능 여부를 함께 묻는 요청은 `rating`이 아니라 `candidate_judge`다.

`out_of_scope`는 요청 전체가 서비스 범위 밖인 경우에만 사용한다. 범위 안의 의도와 범위 밖의 부가 요청이 섞인 경우에는 범위 안의 주된 의도를 분류하고, V0 라우팅 이후의 답변 정책에서 범위 밖 부분을 제한한다.

## 6. 출력 계약

출력은 다음 네 필드만 포함한다.

```json
{
  "question_type": "candidate_judge",
  "required_evidence": ["circuit", "datasheet"],
  "next_action": "search_agent",
  "reason_code": "CANDIDATE_JUDGE"
}
```

위 JSON은 형식 예시다. 각 필드의 허용값은 이 절의 표와 규칙을 따른다. 추가 필드, 설명문과 Markdown을 출력하지 않는다. 허용 목록에 없는 값을 생성하지 않는다.

### `required_evidence`

`required_evidence`는 현재 부족한 근거가 아니라 해당 질문에 답하기 위해 필요한 전체 근거 종류다.

| `question_type` | 기본 근거 |
|---|---|
| `out_of_scope` | `[]` |
| `insufficient_information` | `[]` |
| `role` | `["circuit"]` |
| `rating` | `["datasheet"]` |
| `candidate_find` | `["circuit", "datasheet"]` |
| `candidate_judge` | `["circuit", "datasheet"]` |

`approved_case`는 사용자가 과거 승인 사례를 요구하거나 승인 사례 재사용이 질문 해결에 필요한 경우에만 추가한다. 근거 배열의 순서는 항상 `circuit`, `datasheet`, `approved_case`다.

### `reason_code`

`reason_code`는 `question_type`과 다음과 같이 일치해야 한다.

| `question_type` | `reason_code` |
|---|---|
| `candidate_find` | `CANDIDATE_FIND` |
| `candidate_judge` | `CANDIDATE_JUDGE` |
| `rating` | `RATING` |
| `role` | `ROLE` |
| `out_of_scope` | `OUT_OF_SCOPE` |
| `insufficient_information` | `INSUFFICIENT_INFORMATION` |

## 7. 라우팅과 종료

`next_action`은 현재 상태에서 다음 규칙으로 선택한다.

1. `out_of_scope` 또는 `insufficient_information`이면 `refuse`를 선택하고 종료한다.
2. `role`이면 `circuit_agent`를 선택한다. 이 경우 `circuit_agent`의 답변을 전달하고 종료한다.
3. 교체 질문에서 필요한 회로 근거가 아직 없으면 `circuit_agent`를 선택한다. 결과를 상태에 저장한 뒤 Supervisor를 다시 호출한다.
4. 필요한 데이터시트 또는 승인 사례 근거가 아직 없으면 `search_agent`를 선택한다. 결과를 상태에 저장한 뒤 Supervisor를 다시 호출한다.
5. 판정에 필요한 근거가 모두 준비되었으면 `judge_answer_agent`를 선택한다. 해당 에이전트의 판정과 사용자용 답변을 전달하고 종료한다.

동시에 여러 근거가 없으면 회로 근거를 먼저 확보한다. 회로 역할과 사용 조건이 검색 및 판정에 필요한 기준을 제공하기 때문이다.

`circuit_agent`는 `role` 질문에서는 종료 경로이고, 교체 질문의 회로 근거 수집에서는 중간 경로다. `search_agent`는 중간 경로이며 `judge_answer_agent`와 `refuse`는 종료 경로다.

## 8. 오류 처리

| 오류 | 처리 |
|---|---|
| JSON 또는 스키마 파싱 실패 | 같은 입력과 프롬프트로 최대 2회 재시도 |
| 허용하지 않은 값 또는 추가 필드 | 스키마 실패로 기록 |
| `question_type`과 `reason_code` 불일치 | 의미 일관성 실패로 기록 |
| 필요한 근거 누락 또는 불필요한 근거 추가 | evidence 오류로 기록 |
| 현재 상태와 맞지 않는 `next_action` | routing 오류로 기록 |
| timeout, 429, 5xx 또는 연결 오류 | 모델 실패로 기록하고 provider fallback을 사용하지 않음 |

첫 응답의 결과와 재시도 후 최종 결과를 분리하여 기록한다. 비교 평가에서는 모델 출력을 조용히 수정하지 않는다.

## 9. 평가 설계

### 공통 조건

- 세 후보 모델에 같은 프롬프트와 입력을 사용한다.
- 같은 구조화 출력 스키마와 테스트 사례를 적용한다.
- 같은 재시도 상한을 적용한다.
- 가능한 범위에서 같은 생성 조건을 사용한다.
- provider fallback을 허용하지 않는다.
- 실제 모델 ID, provider, latency, token usage와 비용을 기록한다.

API별 구조화 출력 방식과 지원 파라미터의 차이는 결과 문서에 남긴다. 동일 조건은 각 API가 지원하는 범위에서 유지하며, 지원하지 않는 파라미터를 억지로 모사하지 않는다.

### 평가셋

1. 기존 동결 70문항은 기존 결과와 호환되는 `question_type` 기준선에 사용한다. 현재 객관적 gold가 있는 관련 35문항만 Accuracy와 Macro-F1에 포함한다.
2. 별도 V0 상태 라우팅 평가셋에는 `required_evidence`와 `next_action` gold를 사전 고정한다. 최초 요청, 일부 근거만 확보된 상태, 필요한 근거가 모두 확보된 상태, 검색 실패, 부족 정보와 복합 의도 사례를 포함한다.

기존 동결 파일과 그 hash는 수정하지 않는다. 별도 평가셋은 기존 평가 결과와 섞지 않고 독립된 버전과 hash를 가진다.

### 지표

- `question_type` Accuracy와 Macro-F1
- First-pass Schema Valid Rate
- Final Schema Valid Rate
- `required_evidence` Exact Match
- `next_action` Accuracy
- 네 필드 조합의 의미 일관성 위반 수
- 동일 입력 반복 시 결정 일치율
- latency, token usage와 비용

현재 gold가 없는 필드에는 정확도 수치를 만들지 않는다. V0 상태 라우팅 평가셋의 gold는 모델 결과를 보기 전에 사람이 검토하고 고정한다.

## 10. 프롬프트 인젝션 후속 단계

V0 평가에서는 정상 요청의 기준 성능을 먼저 측정한다. 이후 별도 설계에서 다음 공격면을 다룬다.

- 사용자 입력의 직접 프롬프트 인젝션
- 검색 문서 또는 데이터시트에 포함된 간접 프롬프트 인젝션
- 서브 에이전트 결과에 포함된 지시 위장 텍스트
- 출력 스키마 이탈 또는 권한 밖 도구 호출 유도

방어 적용 전과 후에 같은 정상 평가셋을 실행해 회귀를 확인하고, 별도 공격 평가셋으로 방어 효과를 측정한다.

## 11. 완료 조건

Supervisor Prompt V0 설계는 다음 조건을 만족할 때 구현 계획으로 전환할 수 있다.

- 역할, 입력 경계, 여섯 질문 유형과 분류 우선순위가 명시되어 있다.
- 네 출력 필드의 의미와 허용값이 명시되어 있다.
- 근거 선택과 상태별 라우팅 규칙이 모순 없이 연결된다.
- 중간 경로와 종료 경로가 구분되어 있다.
- 세 모델 비교 조건, 오류 처리와 평가 지표가 정의되어 있다.
- 프롬프트 인젝션 방어가 별도 후속 범위로 분리되어 있다.
- 사용자 검토를 통과한다.
