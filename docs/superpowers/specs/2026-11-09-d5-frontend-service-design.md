# D5 프론트엔드 서비스 설계

상태: 사용자 승인

작성일: 2026-11-09

## 1. 목적

SojaFit의 D5 멀티 에이전트 파이프라인을 로그인한 사용자가 브라우저에서 끝까지 사용할 수 있게 한다. 사용자는 공개 데모 회로를 선택하거나 KiCad 넷리스트를 업로드하고, 대상 부품을 골라 질문하며, 데이터시트 근거와 후보별 판정을 확인한다. 부족한 회로 값은 같은 대화에서 보충하고, 최종 판정을 사람이 승인한 뒤에만 견적과 승인 사례를 저장한다.

프론트엔드는 React + Vite + TypeScript로 만든다. D5의 계획·검색·판정·재계획·답 검사 순서를 바꾸거나 브라우저에서 다시 구현하지 않는다.

## 2. 성공 기준

- 로그인한 사용자가 데모 회로와 업로드 회로로 프로젝트를 만들 수 있다.
- 업로드 원본은 정규화가 끝난 뒤 남지 않고, 정규화된 회로 데이터만 해당 사용자 프로젝트에 저장된다.
- 사용자가 대상 부품과 질문을 보내면 D5가 같은 thread에서 실행되고 진행 단계가 표시된다.
- D5 판정 인터럽트가 요구한 회로 값을 사용자가 입력하면 멈춘 노드부터 재개된다.
- 최종 답, 데이터시트 근거, 후보별 5종 판정, 거절 사유를 D5 상태와 일치하게 표시한다.
- 가격·재고는 `/api/prices`에서 화면을 열 때 조회하며 DB·대화·체크포인트·견적에 저장하지 않는다.
- 승인 전에는 견적과 승인 사례가 저장되지 않는다.
- 프로젝트·대화·승인 자료는 소유 사용자와 관리자 권한 경계를 지킨다.
- 새로고침과 재로그인 뒤에도 프로젝트와 완료된 대화를 다시 열 수 있다.

## 3. 범위

### 포함

- React + Vite + TypeScript 프론트엔드
- 같은 출처 FastAPI 배포와 개발용 Vite `/api` 프록시
- 비밀번호 로그인, Google 관리자 로그인, 로그아웃, 관리자 계정 관리 화면
- 사용자별 프로젝트 CRUD
- 공개 데모 회로 5종 선택
- KiCad `.net` 넷리스트 업로드, 검증, 정규화, 대상 부품 선택
- D5 질문 실행, 단계 진행 표시, 인터럽트 재개, 완료 대화 조회
- 근거·판정·거절·가격·재고 표시
- 사람 승인, 견적 저장, 승인 사례 저장과 삭제
- 사용자별 DB 권한, 영속 체크포인트, 공통 오류 응답
- 프론트 단위·통합 테스트와 API·D5 서비스 회귀 테스트

### 제외

- D4 실행 선택 UI
- D5의 Supervisor·문서 에이전트·판정 에이전트 판단 규칙 변경
- 현재 없는 외부 웹 조회 에이전트
- 실제 주문·결제와 판매처 비교
- Mouser 가격·재고 저장 또는 데모 가격표 생성
- 원본 회로도·PCB 파일 업로드
- 실시간 공동 편집과 프로젝트 공유
- 모바일 전용 앱

외부 웹 조회는 D5 자체의 새 에이전트와 평가가 필요한 별도 기능이다. 이 설계에서는 코퍼스 밖 요청을 현재 D5의 거절 계약대로 처리한다.

## 4. 핵심 결정

### 4.1 서비스 파이프라인

- 서비스 실행 정본은 `backend/multi_agent/build.py`의 D5다.
- D4는 평가 기준선으로만 남고 서비스 API나 화면에 노출하지 않는다.
- 프론트는 에이전트 선택, 검색어, 판정 결과를 정하지 않는다.
- API 어댑터는 사용자 입력을 D5 입력으로 바꾸고 D5 상태를 안전한 응답 DTO로 바꾸는 일만 한다.

### 4.2 회로 입력과 보관

- 프로젝트 생성 시 공개 데모 회로 선택 또는 KiCad `.net` 업로드 중 하나를 고른다.
- 업로드는 UTF-8 텍스트, 최대 5 MiB, KiCad export 최상위 구조와 부품·넷 존재 여부를 검사한다.
- 파일명과 업로드 경로를 서버 파일 경로로 사용하지 않는다.
- 파서는 부품 참조자·값·footprint와 넷별 핀 연결만 정규화한다.
- 원본 바이트는 요청 처리 중에만 사용하고 정규화 성공·실패 뒤 폐기한다.
- DB에는 정규화 JSON, 원본 SHA-256, 파서 버전, 생성 시각만 저장한다. 원본 본문과 로컬 경로는 저장하지 않는다.
- 프로젝트 삭제 시 정규화 회로, thread, 메시지, 체크포인트, 견적, 승인 사례 연결을 한 트랜잭션으로 삭제한다.

### 4.3 배포

- 개발: Vite 개발 서버가 `/api`를 FastAPI로 프록시한다.
- 운영: Docker 다단계 빌드가 프론트엔드를 먼저 빌드하고 FastAPI 이미지에 정적 산출물만 복사한다.
- FastAPI는 `/api/*`, `/health`, Google callback을 먼저 처리하고 그 밖의 화면 경로는 React 진입 파일로 돌린다.
- 인증은 현재 HttpOnly 서버 세션 쿠키와 같은 출처 정책을 그대로 사용한다. 토큰을 브라우저 저장소에 두지 않는다.

## 5. 화면 구조

### 5.1 공통 화면

- `/login`: 비밀번호 로그인, 설정된 경우 Google 관리자 로그인
- `/app`: 사용자 작업대
- `/admin/users`: 관리자 전용 계정 목록과 일반 사용자 활성 상태 변경

### 5.2 작업대

작업대는 세 영역으로 구성한다.

- 왼쪽: 사용자 프로젝트 목록, 새 프로젝트, 회로 출처, 삭제
- 가운데: 선택한 대상 부품, D5 대화, 진행 단계, 추가 정보 입력, 질문 작성
- 오른쪽: 회로 주변 연결, 데이터시트 근거, 후보별 판정, 가격·재고, 승인·견적

좁은 화면에서는 왼쪽을 서랍으로, 오른쪽을 `회로·근거·판정·가격·승인` 탭으로 바꾼다. 가운데 대화는 항상 유지한다.

### 5.3 표시 원칙

- 판정 5종은 `동일품`, `사양 동등`, `역할상 충분`, `불충족`, `문서로 확인 안 됨`을 그대로 쓴다.
- 판정 바로 옆에 근거 문서명·쪽·표·행 또는 절을 표시한다.
- 모든 판정 결과에 “같은 동작은 보장하지 않는다”를 표시한다.
- 패키지 차이와 기판 수정 필요 여부를 판정과 별도 항목으로 표시한다.
- 내부 prompt, 모델 원문, `Plan`·`TaskReport` 전문, 서버 경로와 예외 원문은 표시하지 않는다.
- 요청 실패 화면에는 공통 오류의 `error.message`와 문의용 `request_id`만 표시한다.

## 6. D5 데이터 흐름

1. 사용자가 프로젝트와 대상 부품을 선택한다.
2. 프론트가 질문을 thread run API에 보내고 SSE 응답 스트림을 연다.
3. 서버가 사용자·프로젝트 소유권과 실행 중인 run 부재를 확인한다.
4. 서비스 어댑터가 질문, 대상, 사용 조건, 정규화 회로 주변 정보를 D5 입력으로 만든다.
5. D5가 입력 읽기 → 사실 확인 → Supervisor 계획을 실행한다.
6. 문서·판정 할 일은 D5의 `Send` 계약대로 실행하고 결과를 모은다.
7. 재시도 가능한 실패면 D5가 한 번 재계획한다.
8. 판정 값이 부족하면 LangGraph 인터럽트를 영속 체크포인트에 남기고 `requires_input`으로 끝낸다.
9. 사용자가 요구된 값을 보내면 같은 thread와 checkpoint에서 `Command(resume=...)`로 재개한다.
10. D5가 답 검사 뒤 완료 또는 거절 상태를 저장한다.
11. 프론트는 완료 상태의 답·근거·판정·거절과 `price_parts`를 표시한다.
12. `price_parts`가 있으면 별도 `/api/prices`를 호출하고 응답을 화면 메모리에만 둔다.
13. 승인 가능한 판정은 사람이 확인한 뒤 승인 API를 호출한다.

프론트가 표시하는 진행 단계는 D5의 `path`와 run 상태에서 만든다. 허용 표시는 `입력 확인`, `사실 확인`, `계획`, `문서 검색`, `판정`, `결과 정리`, `답 검사`, `추가 정보 필요`, `완료`, `거절`이다. 내부 노드 원문과 모델 chain-of-thought는 노출하지 않는다.

## 7. API 경계

모든 API는 현재 세션 인증과 공통 `X-Request-ID`·JSON 오류 계약을 사용한다.

### 7.1 프로젝트와 회로

- `GET /api/projects`: 내 프로젝트 요약 목록
- `POST /api/projects`: 데모 회로 ID로 프로젝트 생성
- `POST /api/projects/upload`: multipart `.net`을 검증·정규화해 프로젝트 생성
- `GET /api/projects/{project_id}`: 회로 요약, 대상 후보 부품, 최근 thread
- `PATCH /api/projects/{project_id}`: 프로젝트 이름과 선택 대상 변경
- `DELETE /api/projects/{project_id}`: 소유 자료 전체 삭제
- `GET /api/demo-circuits`: 공개 데모 회로 목록과 라이선스 표시 정보

업로드 성공 응답에는 원본 본문 대신 정규화 결과 요약과 선택 가능한 부품 참조자만 포함한다.

### 7.2 대화와 D5 실행

- `GET /api/projects/{project_id}/threads`: 프로젝트 thread 목록
- `POST /api/projects/{project_id}/threads`: 새 thread 생성
- `GET /api/threads/{thread_id}`: 저장된 메시지와 현재 run 상태
- `POST /api/threads/{thread_id}/runs`: 사용자 질문을 저장하고 D5를 실행하며 SSE 진행 이벤트와 최종 결과 전송
- `GET /api/runs/{run_id}`: 새로고침·연결 종료 뒤 저장된 run 상태와 결과 조회
- `POST /api/runs/{run_id}/resume`: 인터럽트가 요구한 값을 제출하고 재개 과정을 SSE로 전송

한 thread에는 동시에 run 하나만 허용한다. 중복 전송은 `409 run_in_progress`로 거절한다. 실행·재개 요청은 `fetch`의 응답 스트림으로 `text/event-stream`을 읽는다. 별도 백그라운드 큐를 만들거나 응답을 먼저 끝낸 뒤 D5를 실행하지 않는다.

SSE 이벤트는 `run_started`, `status`, `requires_input`, `completed`, `refused`, `failed` 여섯 종류다. 첫 이벤트가 `run_id`를 준다. 토큰 단위 모델 출력은 전송하지 않는다. 서버는 완료·거절·실패 상태를 DB에 저장한 뒤 마지막 이벤트를 보낸다. 연결이 끊기면 프론트는 `GET /api/runs/{run_id}`로 저장된 상태를 확인하며 같은 질문을 자동 재전송하지 않는다. 아직 실행 중이면 상태 조회만 반복하고, 실패했으면 사용자가 명시적으로 새 run을 시작한다.

### 7.3 승인·견적·기억

- `POST /api/messages/{message_id}/approvals`: 완료된 판정의 사람 승인
- `GET /api/projects/{project_id}/quotes`: 저장된 견적 목록
- `POST /api/messages/{message_id}/quotes`: 승인된 판정으로 견적 저장
- `GET /api/approved-cases`: 현재 사용자의 승인 사례 목록
- `DELETE /api/approved-cases/{case_id}`: 틀리거나 불필요한 사례 삭제

승인과 견적은 성공한 판정 메시지의 immutable snapshot을 참조한다. 가격·재고와 Mouser 응답 필드는 승인·견적·사례 스키마에 두지 않는다. 견적 화면을 열 때 품번으로 가격 API를 다시 호출한다.

## 8. 저장 모델

- `projects`: 소유 사용자, 이름, 회로 출처 종류, 생성·수정 시각
- `circuits`: 프로젝트, 정규화 연결 JSON, 원본 SHA-256, 파서 버전
- `threads`: 프로젝트, LangGraph thread ID, 생성·수정 시각
- `messages`: thread, 역할, 사용자 글 또는 안전한 D5 결과 DTO, 생성 시각
- `runs`: thread, 상태, 현재 단계, 오류 코드, 시작·종료 시각
- LangGraph checkpoint tables: thread별 D5 영속 상태와 interrupt 재개 정보
- `approvals`: 승인자, 대상 메시지, 판정 snapshot, 승인 시각
- `quotes`: 승인, 품번·수량·판정 근거 snapshot, 생성 시각
- `approved_cases`: 사용자, 승인, 재사용할 회로 조건·판정 요약, 생성 시각

모든 사용자 소유 행은 `user_id`를 직접 또는 프로젝트 관계로 검증한다. 관리자 계정 관리 권한이 다른 사용자의 프로젝트·대화 내용 열람 권한을 자동으로 주지 않는다.

## 9. D5 응답 DTO

브라우저에는 다음 값만 전달한다.

- `answer`: 사용자용 최종 답
- `status`: `completed`, `requires_input`, `refused`, `failed`
- `stage`: 허용된 진행 단계
- `question_type`: D5의 여덟 질문 유형
- `evidence`: 문서명, 쪽, 표·행 또는 절, 인용 번호
- `judgement`: 후보별 판정, 조건별 비교, 패키지 차이, 확인 불가 항목
- `price_parts`: 화면이 가격 API에 물을 품번
- `refusal`: 사용자용 코드와 문구
- `interrupt`: 필요한 값의 코드, 사용자용 이름, 단위, 설명
- `request_id`: 요청 추적 ID

`facts`, `plan`, `reports`, `counters`, `check`는 서버 검증과 관측에 남기되 브라우저 DTO에는 그대로 싣지 않는다. `check` 실패는 검증 실패 거절로 변환한다.

## 10. 오류와 복구

- 400: 파싱할 수 없는 넷리스트 또는 누락 필드
- 401: 로그인 필요
- 403: 다른 사용자의 프로젝트·thread·승인 자료 접근
- 404: 리소스 없음
- 409: 같은 thread 실행 중, 이미 승인됨, 승인 전 견적 요청
- 413: 5 MiB를 넘는 업로드
- 422: 허용하지 않은 부품 참조자·회로 값·가격 품번
- 503: 검색·모델·체크포인트 등 일시적 서비스 장애

서버는 예외 원문, prompt, API key, 업로드 본문, Mouser 요청 주소와 응답을 로그에 남기지 않는다. D5의 정상 거절과 시스템 실패를 구분한다. 시스템 실패는 완료 답으로 저장하지 않으며 같은 사용자 요청을 자동 재실행하지 않는다.

## 11. 프론트엔드 구성

- React Router: 로그인, 작업대, 관리자 경로
- TanStack Query: 프로젝트·thread·메시지·승인·견적 서버 상태
- React Context: 현재 사용자와 선택 프로젝트처럼 작은 앱 상태
- 기본 `fetch` 래퍼: 같은 출처 cookie, 공통 오류와 request ID 처리
- SSE 훅: streaming fetch 해석, 연결 종료 뒤 run 상태 복구, 완료 후 query 무효화
- 별도 Redux·Zustand는 사용하지 않는다.

주요 컴포넌트는 `ProjectSidebar`, `CircuitSetup`, `ConversationPanel`, `RunStatus`, `InterruptForm`, `EvidencePanel`, `JudgementTable`, `PricePanel`, `ApprovalPanel`, `QuotePanel`, `AdminUsersPage`로 나눈다. 각 컴포넌트는 API DTO만 받고 D5 내부 상태를 해석하지 않는다.

## 12. 검증

### 백엔드

- 업로드 형식·크기·경로·원본 폐기와 정규화 테스트
- 사용자별 프로젝트·thread·메시지 권한 테스트
- D5 의존성 조립과 기존 그래프 경로 회귀 테스트
- 영속 checkpoint를 사용한 interrupt·resume 테스트
- SSE 상태 순서·연결 종료 뒤 상태 조회·완료 복구 테스트
- 가격 응답 비저장 테스트
- 승인 전 견적 거부와 승인 뒤 snapshot 저장 테스트
- 프로젝트 삭제 cascade와 승인 사례 삭제 테스트

### 프론트엔드

- 로그인·로그아웃·401 복구
- 데모 선택·업로드 오류·대상 부품 선택
- 질문 전송과 실행 중 중복 방지
- 진행 단계, 추가 정보 폼, 완료·거절·실패 화면
- 근거 인용과 5종 판정 렌더링
- 가격 조회 결과가 캐시 영속 저장소에 남지 않는지 확인
- 승인·견적 조건과 관리자 권한 화면
- 좁은 화면의 서랍·탭 전환과 키보드 접근성

### 통합 수용 흐름

1. 일반 사용자가 로그인하고 데모 회로로 역할 질문을 완료한다.
2. 업로드 회로에서 대상 부품을 선택하고 후보 판정 질문을 보낸다.
3. 추가 값 요구에 답해 같은 D5 run을 재개한다.
4. 근거와 판정표를 확인하고 가격을 별도 조회한다.
5. 승인 뒤 견적과 승인 사례가 저장되고 재로그인 뒤 다시 보인다.
6. 다른 사용자는 해당 프로젝트와 자료에 접근하지 못한다.
7. 프로젝트 삭제 뒤 관련 자료가 조회되지 않는다.

## 13. 구현 순서와 PR 경계

한 PR에 전체를 넣지 않는다.

1. 프론트 기반·같은 출처 배포·기존 인증/관리자/가격 연결
2. 프로젝트·데모 회로·업로드 정규화·대상 선택
3. D5 서비스 조립·영속 thread/checkpoint·질문/재개 API
4. 작업대 대화·SSE·근거·판정·가격 표시
5. 승인·견적·승인 사례와 삭제
6. 전체 통합·접근성·운영 검증

각 PR은 목적 하나, 관련 테스트, 폴더 설명, `SOJAFIT.md` 트리 한 줄, `docs/worklog/osc.md` 기록을 함께 갖는다. `SPEC.md`와 ADR 변경이 필요하면 OSC에서 직접 수정하지 않고 조장에게 정확한 변경안을 전달한다.

## 14. 완료 조건

- D5 내부 판단 순서를 바꾸지 않고 서비스 API에서 실제 D5를 조립한다.
- 데모와 업로드 회로의 동일한 질문 경로가 동작한다.
- interrupt·resume와 새로고침 복구가 영속 checkpoint로 검증된다.
- 근거·판정·거절·가격·승인·견적이 정해진 경계대로 표시·저장된다.
- 가격·재고와 업로드 원본이 저장되지 않는다.
- 사용자별 권한과 삭제가 통합 테스트로 검증된다.
- 프론트·백엔드·저장소 구조 테스트가 통과한다.
- 외부 웹 조회를 구현된 것처럼 표시하지 않는다.
