## 1. 질문과 결론

질문: 1비트로 줄인 사본(`bit(1536)`)으로 후보 N장을 Hamming 거리로 거른 뒤 N장만 정확 코사인으로 다시 재면, 정확 검색 대비 시간이 줄고 결과가 유지되는가.

| 항목 | 값 | 근거 |
|---|---|---|
| 정확 검색 질문당 시간(50문항) | p50 9,353 ms, p95 11,932 ms | `scripts/results/bit_search/bit_search_2026-11-03.json` `exact_ms` 집계 |
| 비트 N=3,200 recall@50 | 0.980, 상위 5 일치 49/50 | 같은 파일 `bq3200` 대 `exact` 집계 |
| 비트 N=3,200 최종 점수(관련 19문항) | 문서 Recall@5 0.737, MRR 0.649, 쪽 적중@5 0.368. 정확 검색과 같음 | `scripts/results/bit_search/bit_search_final_2026-11-03.json` `summary` |
| `retrieve()` 질문당 시간 중앙값 | 6.22초에서 0.89초 | 같은 파일 `summary.exact.sec_p50`, `summary.bit3200.sec_p50` |
| 서비스 반영 | `N_BIT = 3200`. 허용 청크가 N_BIT장을 넘으면 1비트 Hamming 거리로 거른다 | `backend/rag/retrieve.py:26,123-140`, `db/009_chunk_embedding_bits.sql` |

현재 서비스의 비트 표는 `chunk_embedding_bits`(voyage-4-large, `bit(1024)`)다. 이 문서의 측정은 `text-embedding-3-small`(1,536차원)과 임시 표 `exp_bq`로 한 것이다.

## 2. 방법과 환경

| 항목 | 값 |
|---|---|
| 1단계 | 1비트 사본 52,244행 전부를 Hamming 거리로 훑어 후보 N개 선택 |
| 2단계 | 후보 N개만 서비스와 같은 식(`embedding::vector(1536) <=> 질문`)으로 다시 재서 50개 선택 |
| 비교 기준 | 같은 시간대에 돌린 정확 검색(`retrieve.py`의 `_dense`와 같은 쿼리, 인덱스 끔) |
| DB | 운영 Supabase(Nano), pgvector 0.8.2, `embedding`은 `halfvec(1536)`. 운영 표는 바꾸지 않고 실험 표 `exp_bq(chunk_id, bq bit(1536))`를 만들어 측정 뒤 삭제 |
| 질문 | `evals/dataset_v1.jsonl` 50문항의 `input` 전체. 벡터는 `openai/text-embedding-3-small`(OpenRouter)로 1회 생성, 4,663토큰(약 0.1원). 질문 벡터 파일 `q_vectors.npy`는 저장소 밖 |
| 후보 수 N | 400, 800, 1,600, 3,200 |
| 시간 | 맥에서 잰 요청 전체 시간(왕복 포함). 왕복 `SELECT 1` 중앙값 14 ms |
| 정확도 | 정확 검색 상위 50과 비교한 recall@50, 상위 5 일치. 거리가 같은 카드(같은 내용)는 같은 것으로 본다 |
| 스크립트 | [scripts/bit_search/bit_search_exp.py](../../scripts/bit_search/bit_search_exp.py). 단계 `embed`, `setup`, `measure`, `report`, `drop`, 측정 뒤 추가한 `warm`(비트 검색만 이어서 측정), `final` |

## 3. 결과

### 3.1 시간(50문항, ms, 요청 전체)

원시: `bit_search_2026-11-03.json`(번갈아 측정), `bit_search_warm_2026-11-03.json`(비트 검색만 이어서). 아래 값은 두 파일의 원시 배열에서 다시 계산한 p50, p95, 최대이며 문서 값과 일치한다.

| 방식 | 정확 검색과 번갈아 p50 · p95 · 최대 | 비트 검색만 이어서 p50 · p95 · 최대 |
|---|---|---|
| 정확 검색 | 9,353 · 11,932 · 18,897 | - |
| 1단계만 (N=800) | 386 · 676 · 1,314 | 39 · 42 · 56 |
| 1+2단계 N=400 | 278 · 522 · 654 | - |
| 1+2단계 N=800 | 220 · 390 · 593 | - |
| 1+2단계 N=1,600 | 255 · 507 · 1,185 | 110 · 250 · 326 |
| 1+2단계 N=3,200 | 444 · 814 · 1,635 | 148 · 260 · 325 |

- 비트만 이어서 잰 1단계(N=800) 실행 계획: 서버 50 ms, shared hit 1,637, read 0 (`bit_search_warm_2026-11-03.json` `plan_stage1_800`).
- 번갈아 잰 쪽이 느린 것은 정확 검색이 벡터 206 MiB를 훑으며 캐시(shared_buffers 224 MB)에서 비트 표를 밀어냈기 때문이다 [추정]. 서비스는 정확 검색을 하지 않으므로 오른쪽 열이 서비스에 가깝다 [추정].

### 3.2 정확도(정확 검색 상위 50 대비)

| N | 전체 50문항 recall@50 평균 (최소) | 상위 50 완전 일치 | 상위 5 일치 | 관련 25문항 recall@50 평균 (최소) | 관련 상위 5 일치 |
|---|---|---|---|---|---|
| 400 | 0.771 (0.34) | 4/50 | 31/50 | 0.798 (0.46) | 16/25 |
| 800 | 0.872 (0.48) | 9/50 | 40/50 | 0.889 (0.64) | 20/25 |
| 1,600 | 0.949 (0.66) | 21/50 | 47/50 | 0.956 (0.74) | 23/25 |
| 3,200 | 0.980 (0.78) | 33/50 | 49/50 | 0.987 (0.94) | 25/25 |

원시 `bit_search_2026-11-03.json`의 `exact`와 `bq400`~`bq3200`을 다시 비교해 얻은 값과 일치한다.

### 3.3 측정 전 기대와 결과

기대는 측정 전에 정했고 근거는 보고서 판정선 [추정], 2단계 61~138 ms [추정], 공개 실험 top-10 99% [문서]에서 낮춘 값 [추정]이다.

| 항목 | 기대 | 결과 |
|---|---|---|
| 1단계만 (N=800) | 300 ms 아래 | 이어서 잰 값 39 ms로 충족. 번갈아 잰 값은 386 ms |

### 3.4 최종 점수 확인(N=3,200)

사후 선택한 값이므로 위 판정 규칙과 별개의 확인이다. 지표는 `evals/runners/run_retrieval.py`의 문서 Recall@5, MRR, 쪽 적중@5이며 같은 채점 코드를 쓴다. 같은 실행 안에서 운영 Supabase에 붙어 `retrieve(..., method='hybrid')`를 두 번 부른다. 하나는 dense가 정확 검색(인덱스 끔), 하나는 dense만 비트 N=3,200 + 재정렬이다. BM25, RRF, k=5는 같다. 질문 벡터는 `q_vectors.npy`를 쓰고 임베딩 API는 부르지 않는다. 채택 규칙: 비트 쪽 문서 Recall@5가 정확 쪽과 같고 MRR 차이가 0.01 이하.

| dense 방식 | 관련 문항 | 문서 Recall@5 | 문서 MRR | 쪽 적중@5 | 질문당 시간 중앙값 |
|---|---|---|---|---|---|
| 정확 검색 | 19 | 0.737 | 0.649 | 0.368 | 6.22초 |
| 비트 N=3,200 + 재정렬 | 19 | 0.737 | 0.649 | 0.368 | 0.89초 |

- 19문항 모두 상위 5장(파일, 쪽, 카드 글)이 같다(`differ_id_rank_exact_bit` 빈 목록).
- 정확 쪽 점수는 D2 기준선(로컬 compose DB, 0.737 · 0.649 · 0.368)과 같다.
- 시간은 BM25 점수 계산, RRF, 카드 본문 읽기를 포함한 `retrieve()` 전체 시간이다. 질문 벡터는 캐시를 써서 임베딩 호출 시간이 빠져 있다.
- 제외된 6문항은 회로 전용(`circuit_only_skipped`: draft30-e01, e02, m01, m02, h01, h02)이다.
- 판정 규칙을 통과했다: 문서 Recall@5가 같고 MRR 차이가 0이다.
- 검색 실험 전체의 최종 수치 정본은 [EVAL_REPORT.md](../../EVAL_REPORT.md)다.

## 5. 한계

- 미확인: 같은 시간대 정확 검색이 11-02 중앙값 7.2초보다 느렸던 이유. 최종 점수 확인(3.4절)은 관련 19문항만 대상이다.
- 측정은 text-embedding-3-small(1,536차원) 기준이다. 현재 서비스의 voyage-4-large(1,024차원) 비트 표에서는 재측정하지 않았다.
- 시간은 맥에서 잰 요청 전체 시간이며 단일 실행이다. 질문 벡터 파일 `q_vectors.npy`는 레포에 없어 이 스크립트는 그대로 재현되지 않는다.
