# 비트 후보 + pgvector 재정렬 실측 (2026-11-03)

확인일: 2026-11-03 실측, 2026-11-04 저장소에 반영. 원시 결과: `bit_search_2026-11-03.json`(전체), `bit_search_final_2026-11-03.json`(최종 점수 확인), `bit_search_warm_2026-11-03.json`(비트 검색만 이어서 잰 시간). 모두 `scripts/results/bit_search/`에 있다.

조사 보고서 "pgvector 유지하며 검색 속도 높이기"의 1순위 방법을 우리 Supabase(Nano)에서 직접 잰다. 실험 스크립트(`bq_exp.py`)와 질문 벡터(`q_vectors.npy`)는 저장소 밖에 두고 결과만 [scripts/results/bit_search/](../../scripts/results/bit_search/)에 올렸다.

## 무엇을 재나

- 1단계: 벡터를 1비트로 줄인 사본(`bit(1536)`)을 52,244행 전부 Hamming 거리로 훑어 후보 N개를 고른다.
- 2단계: 후보 N개만 지금 서비스와 같은 식(`embedding::vector(1536) <=> 질문`)으로 다시 재서 50개를 남긴다.
- 비교 기준: 같은 시간에 돌린 지금 정확 검색(`retrieve.py`의 `_dense`와 같은 쿼리, 인덱스 끔).

## 조건

- DB: 운영 Supabase. 운영 표는 바꾸지 않는다. 실험 표 `exp_bq(chunk_id, bq bit(1536))`를 만들어 재고 끝나면 지운다.
- 질문: `evals/dataset_v1.jsonl` 50문항의 `input` 전체(v1 베이스라인과 같은 질의 글). 질문 벡터는 `openai/text-embedding-3-small`(OpenRouter)로 한 번 만들어 `q_vectors.npy`에 둔다.
- 후보 수 N: 400 · 800 · 1,600 · 3,200.
- 시간: 맥에서 잰 요청 전체 시간(왕복 포함). 왕복은 `SELECT 1`로 따로 잰다.
- 정확도: 정확 검색 상위 50과 비교한 recall@50, 상위 5가 같은 비율. 거리가 같은 카드(같은 내용 카드)는 같은 것으로 본다.

## 실행 단계

`embed`(질문 벡터) → `setup`(실험 표 생성) → `measure` → `report` → `drop`(실험 표 삭제) 순서다. `warm`은 측정 뒤에 더한 단계다. `measure`에서 1단계만 잰 시간이 1+2단계보다 길게 나와서, 정확 검색을 섞지 않고 비트 검색만 이어서 다시 쟀다.

## 후속: 최종 점수 확인 (N=3,200, 사후 선택)

(11-03 측정 전 기록)

- 후보 N=3,200은 위 결과를 본 뒤에 고른 값이다(사후 선택). 그래서 위 판정 규칙과 별개의 확인으로 둔다.
- 지표: 조 저장소 `evals/run_retrieval.py`가 채점하는 v1 관련 문항(데이터시트 근거가 있는 문항)의 문서 Recall@5 · MRR · 쪽 적중@5. 같은 채점 코드(`run_retrieval.main`)를 그대로 쓴다.
- 비교: 같은 실행 안에서 운영 Supabase에 붙어 `retrieve(..., method='hybrid')`를 두 번 부른다. 하나는 지금 dense(정확 검색, 인덱스 끔), 하나는 dense만 비트 N=3,200 + 재정렬로 바꾼 것이다. BM25 · RRF · k=5는 같다. 질문 벡터는 `q_vectors.npy`를 쓰고 임베딩 API는 부르지 않는다.
- 판정 규칙: 비트 쪽 문서 Recall@5가 정확 쪽과 같고 MRR 차이가 0.01 이하일 때만 비트 방식 채택의 근거로 쓴다. 아니면 쓰지 않는다.
