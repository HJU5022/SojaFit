# 로그인 이메일 암호화 정책 선택지

- 작성일: 2026-11-04
- 기준 코드: 로컬 STH `fdbe30a`; 현재 작업 트리의 `backend/auth.py`, `backend/main.py`, `db/003_auth.sql`, `docs/specs/login-auth.md` 대조
- 상태: 사용자가 A안을 선택 방향으로 제시했다. 팀 합의와 실제 DB 제공자 설정 확인은 남아 있으며, 이 문서만으로 운영 변경 승인을 뜻하지 않는다.
- 범위: SojaFit 로그인 식별 이메일 저장 및 조회. 비밀번호, 세션 토큰, 평가 계정의 전달 방식은 별도 항목으로 구분한다.

## 현재 구조와 전제

- `users.login_id`는 이메일 원문을 `VARCHAR(100) UNIQUE`로 저장하고, 로그인은 `WHERE login_id = 이메일`로 계정을 찾는다.
- 관리자 사용자 목록은 이메일을 서버에서 마스킹해 돌려준다. 계정 생성 CLI와 로컬 데모 시드도 이메일을 사용한다.
- 비밀번호는 salt가 있는 scrypt 해시로 확인한다. 복호화하면 안 된다. 세션 토큰 원문도 클라이언트 쿠키에만 있고, DB에는 `AUTH_SECRET` 기반 HMAC 값만 저장한다. 둘 다 이메일 필드 암호화와는 별개다.
- 현 테스트에서는 서비스 DB와 연결된 이메일·계정이 확인되지 않았다. 서비스 DB 작업은 식별·접근이 해결된 뒤 별도로 진행한다.
- 사용자가 정한 경계: pgvector 확장·코퍼스·임베딩 표와 데이터는 이 정책 작업에서 변경하지 않는다.

|---|---|---|---|---|---|
| A. DB 저장 암호화와 접근 통제 | DB 엔진을 통해서는 읽힐 수 있음 | 현재 방식 그대로 | 거의 없음 | 낮음 | 매체·백업 탈취 위험을 줄이는 것이 목표이고 DB 권한자에게 이메일이 보이는 것을 허용할 때 |
| B. 앱 계층 필드 암호화 + HMAC 검색값 | 암호문만 저장 | 정규화 이메일의 HMAC 검색값으로 일치 조회 | 중간. users 스키마·로그인·CLI·관리자 목록·마이그레이션 변경 | 중간 이상. 암호화 키·검색 키·회전/복구 필요 | DB 덤프나 DB 읽기 권한만으로 평문 이메일을 보지 못하게 해야 할 때 |

| D. 단순 결정적 이메일 암호화 | 암호문 저장 | 매번 같은 암호문으로 비교 | 작음~중간 | 얼핏 낮아 보이나 누출·키 관리 위험 큼 | 권장하지 않음. 빈도·동일성 정보가 드러나며 암호화 인증/회전 설계가 약해지기 쉬움 |

## A. DB 저장 암호화와 접근 통제

**프로젝트 적용 범위**

- `login_id`, 로그인 API, 유일성 제약은 그대로 둔다.
- Supabase/DB 제공자의 저장 매체·백업 암호화와 DB 역할 권한, 연결 TLS, Secret 접근 권한을 확인한다. 현재 서비스 DB 제공자 설정은 확인되지 않았다.

**용이성과 고려사항**

- 구현과 데이터 이관이 가장 쉽고 기존 로그인 흐름을 깨지 않는다.
- 저장 매체나 백업 파일만 분리 유출되는 위험을 줄일 수 있지만, DB에 쿼리 권한을 가진 운영자·앱 계정에게 이메일은 평문으로 보일 수 있다. 앱 계층 암호화와 같은 보호 수준이 아니다.
- 실제 서비스 제공자에서 저장 시 암호화, 백업 암호화, 연결 TLS, 권한 경계를 확인해야 한다. 이름만으로 Supabase 설정을 추정하지 않는다.

## B. 앱 계층 필드 암호화와 HMAC 검색값

**프로젝트 적용 범위**

- `users.login_id`의 평문 저장을 중단하고 암호문(예: `login_id_ciphertext`)과 검색용 HMAC(예: `login_lookup_hmac`)을 저장한다. 필요하면 키 식별자/버전을 함께 저장한다.
- 로그인 입력 이메일은 현재 규칙대로 trim/lowercase 정규화한 뒤 검색 키로 HMAC해 계정을 찾는다. HMAC 키는 이메일 암호화 키와 분리한다. HMAC 인덱스는 이메일 원문을 숨기지만 같은 이메일이 반복되는 사실과 계정 수는 드러낸다.
- 관리자 목록에서 도메인을 포함한 현재 마스킹을 유지해야 하면 앱이 권한 확인 후 이메일을 복호화해 마스킹하거나, 별도 표시 정책을 정한다. 평문 이메일을 API 응답에 추가하지 않는다.
- 계정 생성 CLI, 데모 시드, 로그인, 관리자 목록, 이메일 UNIQUE/정규화 규칙, 비밀번호 재설정/계정 삭제(현재 미구현), DB 이관을 함께 바꿔야 한다.

**용이성과 고려사항**

- 이메일 로그인 UX를 유지하면서 DB 덤프에 평문 이메일이 보이는 것을 줄일 수 있다. 다만 애플리케이션이 실행 중이거나 키 사용 권한을 가진 환경에서는 복호화가 가능하다.
- 무작위 nonce를 쓰는 인증된 암호화(AEAD)를 사용해야 하며 동일 키에서 nonce를 재사용하면 안 된다. HMAC 조회 키를 암호화 키와 분리하고, 두 키의 보관·접근·백업·회전·복구 담당을 정해야 한다.
- Cloud KMS envelope encryption은 키 통제와 감사 경계를 강화할 수 있지만 IAM, API 호출, 배포 설정, 운영 비용·지연 검토가 추가된다. Secret Manager에 애플리케이션 키를 보관하는 단순안도 런타임 권한과 회전/복구 절차가 필요하다.
- 기존 `login_id`의 평문 값을 옮기는 일회성 변환은 기존 DB 접근권한과 백업·로그에 남아 있는 과거 값까지 자동으로 지우지 않는다. 전환 전후 정합성 대조와 복구 계획이 있어야 한다.
- 키를 잃으면 이메일을 되살릴 수 없고, 키를 바꾸면 조회용 HMAC도 달라질 수 있다. 조회 키 회전은 전체 HMAC 재계산과 중복 확인을 요구하므로 단순 Secret 교체로 취급하면 안 된다.
- 현재 STH의 주요 문서 `SPEC.md`는 조장 소유다. 이메일 저장 구조 변경을 선택하면 조장이 기능 기준·정책을 먼저 SPEC에 반영하고, 승인된 작업서와 테스트를 만든 뒤 구현한다.

## C. 이메일 대신 별칭 또는 외부 인증 식별자

**프로젝트 적용 범위**

- 평가·내부 계정을 `user-<무작위 식별자>` 같은 별칭으로 로그인하게 하거나, 외부 인증 제공자의 안정된 주체 ID만 내부 `users` 키에 연결한다.
- 이메일을 계정 생성·관리 API·로그인 입력에서 제거하거나 외부 IdP가 관리한다. 현재 기능 명세가 이메일·비밀번호 직접 로그인을 정하므로 계약과 평가 절차도 바뀐다.

**용이성과 고려사항**

- 계정 DB에 이메일을 아예 저장하지 않는 목표에는 가장 직접적이다.
- 팀·평가자가 계정 별칭을 안전하게 발급·회수·전달하고 사용자를 식별하는 절차가 필요하다. IdP를 택하면 로그인 연동, 사용자 매핑, 장애 시 접근 회복이 추가된다.
- 현 로그인 기능을 빠르게 유지해야 할 때는 범위가 크며, 선택 시 별도 SPEC/ADR과 평가 시나리오 수정이 필요하다.

## D. 단순 결정적 암호화

**프로젝트 적용 범위와 용이성**

- 정규화 이메일이 같으면 항상 같은 암호문이 나오도록 해 현재 `=` 조회를 유지하려는 방식이다.
- 변경 폭은 작아 보이지만 반복 이메일의 동일성·빈도가 노출된다. 인증 없는 암호 모드, 고정 nonce, 비밀번호 기반 암호화 등으로 축약하면 위변조 감지나 키 보호가 약해질 수 있다.
- 선택지 B의 무작위 nonce 인증 암호화 + 별도 HMAC 검색값이 이 요구를 더 분명하게 처리하므로 이 안은 권장하지 않는다.

## 권장 논의안 (팀 승인 전)

- 목표가 DB 덤프/읽기 권한자에게 평문 이메일을 보이지 않는 것이라면 B를 선택한다. 임의의 암호화 방식을 만들지 않고 검토된 AEAD/키 관리 라이브러리와 키 관리 경계를 채택한다.
- 목표가 저장 매체 암호화와 최소 권한이라면 우선 A의 실제 제공자 설정·백업·TLS·접근 권한을 확인한다. 저장 계층 암호화가 앱 계층 필드 암호화를 대신한다고 표현하지 않는다.
- 이메일 수집 자체를 피해야 한다면 C를 검토하되 로그인 계약 변경과 IdP 운영 범위를 별도 결정한다.
- 세 선택 모두 실제 서비스 DB가 식별되고 백업/복구 경로가 확인되기 전에는 운영 데이터에 쓰지 않는다. pgvector 스키마나 데이터는 조사·시험·이관 대상에 포함하지 않는다.

## 현재 진행 방향

- 사용자는 A안(DB 저장 암호화·접근 통제)을 선택 방향으로 제시했다. 앱 계층 이메일 필드 암호화/복호화와 인증 스키마 변경은 하지 않는 방향이다.
- 실제 Cloud Run `DATABASE_URL` 대상은 확인되지 않았다. Supabase라면 공급자 문서는 DB·백업의 저장 암호화와 SSL 연결 설정을 설명하지만, 그 내용은 SojaFit 연결 프로젝트의 설정을 증명하지 않는다.
- A안의 명시적 한계: DB 조회 권한을 가진 앱/운영 역할은 `users.login_id` 이메일 평문을 볼 수 있다. 이 노출을 허용하지 못하면 B안을 다시 검토해야 한다.
- 다음 확인: 실제 DB 제공자·프로젝트, 저장/백업 암호화, 연결 TLS, 앱·운영 역할의 최소 권한과 복구 절차를 읽기 전용으로 확인한다. 연결 문자열은 출력하거나 기록하지 않는다.

## 참고 자료

- Google Cloud, [Envelope encryption](https://docs.cloud.google.com/kms/docs/envelope-encryption): 저장 계층과 앱 계층 암호화, DEK/KEK 분리, envelope encryption 설명.
- Supabase, [Data Residency and Transfers FAQ](https://supabase.com/legal/privacy-resources/data-residency-and-transfers-faq): Supabase 일반 저장·백업 암호화 설명. 특정 프로젝트 확인 결과가 아니다.
- Supabase, [Postgres SSL Enforcement](https://supabase.com/docs/guides/platform/ssl-enforcement): DB 접속 TLS 강제와 PostgreSQL SSL 모드 차이.
- Google Cloud, [Client-side encryption with Tink and Cloud KMS](https://docs.cloud.google.com/kms/docs/client-side-encryption): 애플리케이션에서 데이터 키를 감싸는 방식과 Tink 지원.
- NIST, [Key Management Guidelines](https://csrc.nist.gov/projects/key-management/key-management-guidelines): 키 수명주기와 접근·회전·보호를 암호 구현과 함께 다뤄야 하는 근거.
- Python Cryptographic Authority, [Authenticated encryption primitives](https://cryptography.io/en/stable/hazmat/primitives/aead/): AEAD의 기밀성/무결성, AES-GCM nonce 재사용 주의.

외부 참고는 일반 암호화 설계 근거다. SojaFit DB 제공자의 실제 저장 암호화 설정, 청구액, 팀의 개인정보 정책을 확인한 결과가 아니다.
