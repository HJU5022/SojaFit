# 저장소 PDF 3건 Docling·pdfplumber 대조

> 실행일: 2026-11-03 · 목적: DB 없는 초기 표 파싱 점검 · 최종 판정 정확도 평가 아님

## 실행 조건

- 대상: 저장소의 1N4148 K2301, 1N5817 H2104, BZT52C2V4 G1804 데이터시트 3건.
- 코드: backend.rag.parse의 run과 recall. Docling은 OCR을 끄고 표 구조를 켰다.
- 환경: Windows, Python 3.12.10, Docling 2.145.0, pdfplumber 0.11.10, PyTorch 2.15.0. 실행 환경에서 torch.cuda.is_available()은 false였다.
- 원본 PDF를 수정하지 않았다. 입력 사본, Docling JSON, witness, recall과 로그는 Git 저장소 밖의 사용자 작업공간 mcp-docling-smoke-48nqes1l 폴더에 보관했다.
- Windows 기본 파서에는 파일별 SIGALRM 제한이 없어 별도 상위 프로세스에서 PDF별 600초 제한을 걸었다.
- DB·LLM·검색 API 호출 없이 실행했다. 프로젝트 uv.lock의 ingest 그룹 설치 과정에서 패키지를 내려받았으며 별도 유료 서비스는 호출하지 않았다.

## 문서별 결과

| PDF | 쪽 | Docling 표 | Docling 숫자 → pdfplumber 같은 쪽 텍스트 | PDF 표 영역 숫자 → Docling | 파싱·대조 시간 |
|---|---:|---:|---:|---:|---:|
| 1N4148-SERIES_K2301 | 5 | 5 | 81/81 | 81개 중 누락 0 | 53.02초 |
| 1N5817-SERIES_H2104 | 6 | 6 | 49/49 | 49개 중 누락 0 | 17.39초 |
| BZT52C2V4-SERIES_G1804 | 7 | 7 | 385/385 | 385개 중 누락 0 | 32.29초 |
| 합계 | 18 | 18 | 515/515 | 515개 중 누락 0 | — |

표 숫자 → 텍스트는 Docling 표 셀의 숫자가 같은 쪽 pdfplumber 텍스트 어딘가에 있는지 센다. 반대 방향은 **Docling이 찾은 표의 영역 안에서** pdfplumber로 추출한 숫자가 Docling 표에도 있는지 센다.

따라서 이 수치는 숫자 누락을 점검하는 보조 지표다. Docling이 표 전체를 놓친 경우, 다른 행의 같은 숫자가 우연히 일치한 경우, 단위·시험 조건·품번과 숫자의 연결 오류까지 모두 검증하지는 않는다.

시간은 각 문서의 기존 parser 로그에 기록된 파싱·대조 시간이다. 첫 문서의 모델 초기화와 운영 환경 차이가 있어 공정한 성능 벤치마크가 아니다.

## 대표 정격 행의 좌표 대조

자동 숫자 비교와 별도로 각 PDF의 첫 표에서 대표 행 1개씩 Docling 셀과 그 행의 pdfplumber 좌표 영역 텍스트를 확인했다.

| 문서 | 쪽·표 | Docling 행 | pdfplumber 동일 영역에서 확인한 내용 |
|---|---|---|---|
| 1N4148 K2301 | 1쪽·표 1 | VRRM / 100 / V | V와 아래첨자 RRM, 100 V |
| 1N5817 H2104 | 1쪽·표 1 | VRRM / 20 - 40 / V | V와 아래첨자 RRM, 20 - 40 V |
| BZT52C2V4 G1804 | 1쪽·표 1 | VF at IF=10mA / 1 / V | VF, IF=10mA, 1 V. 아래첨자는 분리 추출 |

이 검사는 선택한 3행의 숫자·단위·문자 출현 확인이다. 모든 표 행의 품번 대응, 최대·최소 의미, 시험 조건, 대체 가능 여부를 검증한 것은 아니다.

## 추가 확인

- 세 PDF 원본의 SHA-256은 실행 후에도 기존 manifest 기록과 일치했다. 기존 DB와 동결 평가셋은 변경하지 않았다.
- 의존성 설치 후 파서·MCP 회귀 테스트 23개가 통과했다.
- 앞선 pypdf 점검에서는 manifest의 전체 문서명에 포함된 SERIES 문자열을 세 PDF의 텍스트에서 찾지 못했다. 이름 전체의 단순 문자열 일치만으로 PDF를 거부하지 않도록 후속 검증 계약을 설계해야 한다.
- 사전 기대인 3건 파싱 성공, 쪽 수 일치, 문서당 표 1개 이상과 숫자 일치율 0.80~1.00은 이 표본에서 충족했다.

## 남은 작업

1. 요청 품번과 개정판이 표지·해당 표 행에 실제로 연결되는지 검증한다. 파일명·텍스트 문자열 출현만으로 판정하지 않는다.
2. 표 병합 셀, 단위, 최솟값·최댓값, 온도·전류 등 시험 조건과 행의 연결을 확대 검증한다.
3. TSC 공식 URL 검증, 파일 크기·시간 제한, 실패 격리, 파싱·대조 결과의 서비스 반영 계약을 정한다.
4. 필요하면 격리 테스트 DB에 표본을 청킹·적재한 뒤 MCP search_corpus의 실제 DB 흐름을 검증한다.
