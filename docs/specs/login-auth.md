# 로그인과 사용자 식별 작업서

## Why
평가자 두 명이 이메일·비밀번호로 로그인하고 사용자별 데이터에 접근해야 한다. 인증 기초가 구현됐으며 업무 데이터 소유권 연결은 미구현이다.

## Goal
두 계정의 로그인·로그아웃과 서버 측 사용자 식별을 제공하고 서로의 데이터 접근을 차단한다. 회원가입, 비밀번호 재설정, 실제 회로·대화·기억·견적 기능 구현은 제외한다.

## What
사전 생성된 계정으로 로그인한다. 잘못된 자격 증명과 비활성 계정에는 같은 실패 메시지를 제공한다. 로그아웃과 세션 만료 후 인증이 필요한 요청은 거부한다. DB 오류는 인증 성공으로 처리하지 않는다.

로그인 이메일은 공백 없이 `local@domain.tld` 형태이고 100자 이하여야 한다. 같은 검증을 계정 생성 CLI와 데모 계정 설정에도 적용한다. 로그인 입력 검증 오류는 제출값을 응답에 되돌려 보내지 않는다. 관리자 계정 목록은 유효한 이메일의 로컬 부분 첫 글자와 도메인만 보이고 나머지는 `***`로 가린다(예: `alice@example.test` → `a***@example.test`). 기존 데이터에 형식이 깨진 이메일이 있어도 목록 요청은 실패하지 않고 이메일을 `***`로 표시한다.

## How
PostgreSQL users와 서버 세션을 사용한다. 비밀번호는 scrypt와 임의 salt로 저장하고 세션 토큰은 난수로 생성한다. AUTH_SECRET이 있으면 HMAC-SHA256 값만 DB에 보관하며, 키 없는 데모 모드는 SHA-256을 사용한다. 데모 외 환경에서는 32바이트 이상 AUTH_SECRET이 필수다. 키를 추가·변경·제거하면 기존 세션은 재로그인해야 한다. 쿠키는 HttpOnly, SameSite=Lax, 배포 환경에서는 Secure다. 상태를 변경하는 브라우저 요청은 동일 출처를 검증한다. 평가 계정은 명령줄에서 비밀번호를 숨겨 입력하며 저장소에 기록하지 않는다. 기존 업무 테이블과 그래프가 미구현이므로 사용자 소유 리소스의 실제 연동은 후속 작업이다.

`users.role`은 `admin` 또는 `user`이며 기본값은 `user`다. 관리자·일반 데모 계정은 새 로컬 Compose DB의 초기화 SQL에서 생성한다. 네 계정 변수가 비어 있으면 `DEMO_MODE=1`일 때만 데모 기본값을 사용하며, 네 값을 모두 설정하면 해당 이메일·scrypt 해시를 사용한다. 기존 계정의 비밀번호나 역할은 덮어쓰지 않는다. 현재 `/login` 화면은 기존 인증 API로 로그인·세션 확인·로그아웃만 수행하며 질문 API와 질문 입력 화면은 아직 제공하지 않는다. 회원가입·비밀번호 재설정·관리자 화면도 제공하지 않는다. 관리자는 API로 계정 목록과 일반 사용자의 활성 상태를 관리한다. 권한은 요청마다 서버 DB에서 확인하며 상태 변경은 동일 출처를 검증한다. 관리자 계정 상태 변경은 관리 API 범위에서 제외한다. 계정 비활성화와 세션 삭제는 같은 트랜잭션에서 처리하며 로그인과 경합할 때 사용자 행을 잠근다. 평가 종료 후 삭제는 비활성 일반 계정만 대상으로 하는 운영자 CLI를 사용한다.
로컬 UI 확인 중 인증 DB를 사용할 수 없을 때는 개발 서버에서 명시적으로 `VITE_DUMMY_AUTH=1`을 설정한 경우에만 프론트 인증 경계를 더미 일반 사용자로 통과시킬 수 있다. 이 플래그는 Vite production build에서는 무시하며 API 응답, 프로젝트 소유권 또는 업무 데이터를 더미로 만들지 않는다.

## AC
- Given 두 계정, When 각각 올바른 비밀번호로 로그인, Then 각자의 사용자 ID를 반환한다.
- Given 잘못된 비밀번호나 없는 계정, When 로그인, Then 같은 오류가 반환된다.
- Given 서로 다른 두 계정, When 각각 로그인 상태를 조회, Then 각자의 서버 검증 사용자 ID와 현재 역할이 반환된다.
- Given 로그아웃 또는 만료, When 인증이 필요한 API를 호출, Then 거부된다.
- Given 인증 서비스 DB가 준비되지 않음, When 로그인, Then 성공하지 않고 오류를 반환한다.
- Given 관리자와 일반 사용자, When 계정 목록 조회 또는 일반 사용자 활성 상태 변경, Then 관리자만 허용한다. 비활성화된 사용자의 모든 세션을 삭제하고, 재활성화 후 기존 세션을 재사용할 수 없다.
- Given 로그인 이메일 또는 비밀번호가 필드 검증에 실패함, When 로그인 요청, Then 오류 응답은 입력값을 포함하지 않는다.
- Given 관리자 계정 목록에 이메일 주소가 있음, When 관리자가 목록을 조회, Then 이메일 로컬 부분은 첫 글자만 보이고 나머지는 `***`로 가려진다.
- Given 이메일이 `local@domain.tld` 형식이 아니거나 100자를 넘음, When 로그인·계정 생성 또는 데모 계정 설정, Then 입력을 거부하고 값을 오류 응답에 포함하지 않는다.
- Given 기존 계정 이메일이 잘못된 형식임, When 관리자가 계정 목록을 조회, Then 요청은 성공하고 해당 주소는 `***`로 표시된다.
- Given 관리자 계정, When 관리 API로 관리자 계정의 상태를 변경하려고 함, Then 거부한다. 관리자 생성은 신뢰된 운영자가 명령줄에서 수행한다.
- Given `VITE_DUMMY_AUTH=1`인 개발 서버, When 프론트 인증 상태를 복원, Then 인증 API를 호출하지 않고 더미 일반 사용자로 화면을 연다. 같은 값의 production build에서는 더미 인증을 사용하지 않는다.

## 후속 연동 계약 초안 (팀 검토 필요)

- 서버가 세션에서 검증한 `users.id`만 회로·분석·대화·장기 기억·견적의 사용자 식별에 사용한다. 클라이언트가 보낸 사용자 ID를 권한의 근거로 삼지 않는다.
- 요청에 포함된 `thread_id`, 회로 ID, 견적 ID는 별도 소유권 검사를 거친 뒤 조회·변경한다. 식별자가 다르다는 것만으로 권한이 보장되지는 않는다.
- 사용자 A와 B로 각각 데이터를 만든 뒤, B가 A의 식별자를 이용해 조회·수정·승인할 수 없는지 테스트한다. 동일 사용자 재접속·서버 재시작 뒤에도 소유권을 유지하는지 확인한다.
- 인증 사용자 ID는 현재 정수이고 그래프 상태와 `memory.namespace`는 문자열을 기대한다. 어떤 경계에서 문자열로 변환할지와 그래프 `thread_id`·Store namespace의 생성·권한 확인 위치, 견적 승인자 역할은 에이전트·서비스 담당이 합의한다. 현재 업무 API, DB Store 및 실제 교차 접근 검증은 구현되지 않았다.

## 로그인 실패 제한

계정별 실패는 15분 구간으로 집계한다. 이 구간에서 5회 실패하면 마지막 실패 시점부터 15분 동안 잠근다. 집계 구간이 만료된 실패는 다음 실패부터 새로 센다. 기존 DB에는 앱을 올리기 전에 `db/005_auth_attempt_window.sql`과 `db/006_user_roles.sql`을 순서대로 한 번씩 적용한다. 기존 잠금의 `locked_until` 의미는 유지한다. 기존 기록의 집계 시작 시각은 알 수 없어 잠금이 없는 과거 실패 기록은 다음 실패에서 새 구간으로 시작한다. 활성 잠금은 유지한다. 계정별 잠금 악용과 서로 다른 계정으로 보내는 분산 요청은 아직 방어되지 않아 배포 전 별도 검토한다.
