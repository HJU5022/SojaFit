# 로그인 마무리 작업 계획

> 2026-11-04 후속 확인: 현재 로컬 `DATABASE_URL`은 아래 테스트 프로젝트를 가리키지 않으며 `TEST_AUTH_DATABASE_URL`은 설정되지 않았다. 테스트 프로젝트의 세 인증 표는 RLS가 켜져 있고 `anon`·`authenticated`의 SELECT 실효 권한이 없다. 아래 연결·RLS 미적용 설명은 변경 전 기록이다. 실제 로그인 및 HTTP Data API 검증은 미실행이다.

> 실행자는 아래 체크박스를 순서대로 진행하고, 실제 결과와 접근 차단은 `../worklog/sth.md`에 남긴다. 사용자는 로컬 구현을 승인했으며, 미확정 개인정보 정책·배포 승인은 별도다.

**Goal:** 비밀번호·개인정보 처리의 현재 상태를 확인하고, pgvector를 변경하지 않는 인증 DB 준비와 배포 로그인 검증을 연결한다.
**Architecture:** 기존 FastAPI → `backend/auth.py` → PostgreSQL 인증 테이블을 유지한다. 별도 인증 테스트 DB에서 먼저 확인하고, 서비스 DB에는 검토된 인증 변경과 합성 계정만 적용한다.
**Tech Stack:** Python 3.12+, uv, FastAPI, psycopg, PostgreSQL, Cloud Run.
**Spec:** `../../SPEC.md` 4·8.6절, `login-auth.md`, `../../db/DB.md`.

## 로그인 후 질문 시연 설계안 — 검토용

이 절은 사용자가 선택한 “로그인 후 질문까지 시연”과 “질문 기록은 저장하지 않음”을 반영한 설계 제안이다. 개인정보 보관 기간과 화면/데이터 범위는 아직 팀장 확인 전이며, 이 절만으로 구현 승인을 뜻하지 않는다.

### 목표와 경계

- 기존 FastAPI 인증 API를 사용해 같은 출처의 로그인 화면에서 로그인하고 질문 하나를 보내 답을 확인한다. 로그아웃도 화면에서 할 수 있게 한다.
- 회원가입, 비밀번호 재설정, 사용자 프로필 입력, 관리자 화면, 영구 대화 기록, 장기 기억, 회로 업로드·저장, 견적 저장은 범위에서 뺀다.
- 이번 시연은 사전 생성한 합성 계정과 민감정보가 없는 질문만 사용한다. 질문 본문은 애플리케이션 DB에 저장하지 않는다.

### 접근안과 권고

| 안 | 구성 | 판단 |
|---|---|---|
| A. 같은 출처의 최소 시연 화면 | FastAPI가 로그인·질문 화면을 제공하고 기존 세션 쿠키로 보호된 질문 API 한 개를 호출한다. 질문 기록은 저장하지 않는다. | **선택됨.** 별도 프론트 앱과 교차 출처 쿠키 설정이 필요 없고, 현재 없는 화면을 최소 범위로 시연할 수 있다. |
| B. 별도 프론트 앱과 영구 대화 | 프론트 앱, 그래프 API, 지속형 체크포인터, 대화별 소유권 저장소를 연결한다. | 사용자별 대화 저장까지 제공하지만 현재 저장소에 대화 API·체크포인터 DB·대화 테이블이 없어 별도 기능 설계와 팀 합의가 필요하다. |
| C. 로그인 화면만 | 로그인·로그아웃만 만들고 질문 흐름은 제공하지 않는다. | 구현은 작지만 사용자가 선택한 “로그인 후 질문 시연”을 충족하지 않는다. |

선택된 방향은 A의 비저장 시연이다. 그래프 요청의 `user_id`는 세션에서 서버가 확인한 값만 사용하고, 클라이언트가 보낸 사용자 ID는 권한 판단에 쓰지 않는다. 요청마다 새 그래프 실행으로 답을 만들며 대화 기록을 남기지 않는다. 장기 기억 `Store`는 연결하지 않는다. 따라서 이번 범위는 저장된 대화·기억을 사용자별로 나누는 기능이 아니라, 로그인하지 않은 요청을 막고 공통 코퍼스에 질문할 수 있게 하는 기능이다.

### 개인정보 보관·삭제 제안

- 계정은 평가용 합성 이메일만 사전 생성한다. 이름·전화번호 등 추가 정보는 받지 않는다. 계정과 비밀번호 해시는 평가에 필요한 동안만 유지하고, 팀장이 평가 종료를 확인하면 계정을 비활성화한 뒤 삭제한다. 정확한 종료일은 팀장이 정한다.
- 평가 종료 정리는 공개 API가 아니라 운영자 전용 절차로 한다. `@example.test` 합성 이메일을 가진 비활성 일반 계정만 기록한 ID로 삭제하고, 그 계정에 연결된 세션은 외래 키 cascade로 지우며, 로그인 실패 표에서는 해당 합성 이메일의 해시 행만 별도로 지운다. 실제 도메인 계정·관리자 계정이나 다른 실패 기록 전체를 지우지 않도록 정리 절차와 확인 결과를 남긴다.
- 세션 쿠키의 기존 만료 기준(30분 유휴, 최대 8시간)을 유지한다. 로그아웃·계정 비활성화는 세션 행을 즉시 삭제한다. 만료 세션은 현재 로그인 요청 때 정리되므로, 다음 로그인이 없으면 만료 행이 DB에 남을 수 있다. 이 보관 한계를 공개하고, 정기 정리를 요구하면 별도 정리 작업을 추가한다.
- 로그인 실패 기록은 이메일 원문 대신 SHA-256 식별자와 실패 횟수만 저장하며 15분 잠금 창에 사용한다. 현재도 로그인 요청 때 만료 기록을 정리하지만 다음 로그인 전까지 행이 남을 수 있다. 평가 종료 때는 계정·세션과 함께 남은 실패 기록도 정리한다.
- 질문은 실제 개인정보나 비밀값을 포함하지 않은 합성 입력만 사용한다. 질문을 로그·추적 데이터에 저장하지 않는 설정을 확인하기 전에는 실사용자 개인정보를 입력하지 않는다. 애플리케이션 DB에 저장하지 않는다는 것만으로 프록시·모델 제공자·추적 서비스의 보관까지 없다고 볼 수 없다.

### 사용자 데이터 소유권

- 현재 인증 API는 `user_id`를 확인하지만, 그래프는 HTTP API로 연결되지 않았고 `AgentState.user_id` 및 장기 기억 namespace 규칙도 로그인 사용자와 연결되지 않았다.
- 제안하는 질문 API는 인증된 세션에서 `user_id`를 가져오며, 요청 본문에 사용자 ID나 대화 ID를 받지 않는다. 질문·답변을 저장하지 않으므로 이번 시연에서 사용자별 대화 목록이나 장기 기억은 제공하지 않는다.
- 데이터시트 코퍼스는 모든 로그인 사용자에게 공통 읽기 전용으로 제공한다.
- 나중에 대화·기억·회로·견적을 저장할 때는 각 레코드에 소유자 `user_id`를 저장하고, 모든 조회·수정·삭제에서 서버 세션 사용자와 소유자가 일치하는지 확인해야 한다. 이 작업 전에는 업무 데이터 사용자별 격리를 완료했다고 말하지 않는다.

### 승인 전 남은 결정

1. 평가 종료 시 합성 계정과 관련 기록을 삭제한다는 보관·삭제 원칙과 평가 종료일을 팀장이 승인한다. 로컬 운영자 삭제 절차는 구현했으며, 격리 DB 통합 검증이 남아 있다.
2. 같은 출처의 FastAPI 화면과 비영구 질문 처리 범위를 팀장이 승인한다.
3. 질문·답변의 프록시·모델·추적 로그 보관을 확인하고, 확인 전 합성 질문만 쓴다는 제한을 승인한다.
4. 팀장이 화면/API 계약과 동일 출처 구조를 `SPEC.md` 및 필요한 ADR에 반영한다. 현재 브랜치 `STH`에서는 해당 주요 문서를 직접 수정하지 않고 조장 반영 대상으로 요청한다.

### 제안 수용 기준 (SPEC 반영 전 초안)

- Given 세션 쿠키가 없거나 만료됨, When 질문 API를 호출, Then `401`을 반환하고 검색·LLM을 호출하지 않는다.
- Given 사용자 A의 유효 세션, When 질문 요청을 보냄, Then 서버 세션의 `user_id`로만 그래프 상태를 만들고 요청 본문의 사용자 ID·대화 ID는 받지 않는다.
- Given 질문을 처리함, When 요청이 끝남, Then 질문·답변·체크포인트·장기 기억을 애플리케이션 DB에 저장하지 않는다.
- Given 로그인 사용자가 데이터시트 코퍼스를 검색함, When 검색 결과를 반환, Then 공통 코퍼스를 읽기만 하고 코퍼스 데이터를 수정하지 않는다.
- Given 로그인·질문 화면에서 로그아웃함, When 보호 API를 다시 호출, Then 세션은 거부된다.
- Given 팀장이 평가 종료를 확인함, When 기록된 합성 평가 계정을 정리함, Then 해당 계정·세션·실패 집계만 삭제하고 다른 계정과 코퍼스는 보존한다.

## 구현 계획 — 로그인 후 질문 시연

> 사용자는 위 검토안과 로컬 구현 시작을 승인했다. 개발은 이 문서의 범위 안에서 진행한다. PR/병합 전에 팀장이 개인정보 보관 종료일·질문 추적 로그 범위를 승인하고 `SPEC.md`/ADR을 반영해야 한다. 구현자 임의로 이 경계를 넓히지 않는다.

**목표:** 사전 생성된 합성 계정으로 같은 출처의 브라우저 화면에 로그인해 데이터시트 질문을 보내고 답을 확인한 뒤 로그아웃할 수 있게 한다. 질문·답변·대화·기억은 애플리케이션 DB에 저장하지 않는다.
**구성:** FastAPI가 기존 세션 API와 그래프 실행을 연결하고 같은 출처의 작은 HTML 화면을 제공한다. 질문 API는 세션에서 확인한 `user_id`만 사용하고 사용자 ID나 대화 ID를 클라이언트에서 받지 않는다.
**기술:** Python, FastAPI, 현재 LangGraph 그래프, 기존 세션 쿠키, `backend/web/templates/`의 단일 HTML 화면.
**기준:** 이 문서의 “로그인 후 질문 시연 설계안”과, 팀장이 반영할 `SPEC.md` 인증·질문 API 계약 및 같은 출처 UI ADR.

### 전역 제약

- 테스트·개발은 격리된 로컬 DB만 사용한다. 현재 `.env`의 실제 DB 대상으로 인증 통합 테스트나 쓰기 작업을 실행하지 않는다.
- 사용자는 합성 계정과 민감정보가 없는 질문만 쓴다. 실제 질문의 외부 로그/추적 보관을 확인하기 전까지 운영 개인정보를 입력하지 않는다.
- 그래프의 LLM 호출은 기존 `backend/services/llm.py` 경계를 그대로 사용한다. API 코드에서 LLM 제공자 라이브러리를 직접 부르지 않는다.
- DB에 사용자 질문·답변·체크포인트·기억을 저장하지 않는다. 코퍼스 검색은 기존 읽기 전용 경로를 사용한다.
- 이 브랜치 `STH`에서는 루트 `SPEC.md`나 `docs/adr/`를 수정하지 않는다. 조장 반영 승인이 구현 선행 조건이다.

### 구현 순서

#### Task 0 — 팀장 반영 사항 (PR/병합 전)

- [x] 작업자는 사용자 승인을 받아 이 문서의 범위 안에서 로컬 구현을 진행한다. 질문에는 합성 데이터만 사용하고 외부 DB·Cloud Run에 배포하지 않는다.
- [ ] PR/병합 전 조장이 평가 종료일, 계정·실패기록 삭제 시점, 질문·답변의 프록시/모델/추적 로그 보관, 같은 출처 화면을 승인한다.
- [ ] PR/병합 전 조장이 루트 `SPEC.md`에 보호 질문 API와 화면 수용 기준을, 필요한 ADR에 같은 출처 UI 결정을 반영한다. STH 작업자는 해당 주요 문서를 수정하지 않는다.

#### Task 1 — 합성 평가 계정의 정확한 삭제 절차

**파일:** `backend/auth.py`, `tests/api/test_auth.py`, `backend/BACKEND.md`.

- [x] 운영자 삭제 API는 `delete_provisioned_user(user_id: int) -> bool`, CLI 옵션은 `--delete-user-id INTEGER`로 구현한다. 없으면 `False`, 비활성 일반 합성 계정(`@example.test`)만 삭제 성공 `True`, 관리자·활성·실제 도메인 계정은 거부한다. 삭제 전 사용자 ID 재입력을 요구한다.
- [ ] 격리 테스트 DB에서 계정 2개와 로그인 실패 집계가 있을 때, 하나의 사용자 ID를 지정한 삭제 함수가 해당 일반 계정과 연결 세션, 그 이메일의 SHA-256 실패 행만 지우고 다른 계정은 남기는 테스트를 먼저 추가한다.
- [ ] 같은 테스트에서 존재하지 않는 ID는 아무 행도 지우지 않고, 관리자 역할 계정은 거부되는지 확인한다.
- [x] 운영자 CLI에 사용자 ID를 명시하는 삭제 동작을 추가한다. 계정 이메일은 표시하지 않고 정확한 ID 재입력을 요구한다. 이메일·비밀번호·해시는 출력하지 않는다.
- [x] 계정 삭제는 트랜잭션으로 처리한다. 사용자 삭제가 외래 키로 세션을 제거하고, 실패기록은 정규화한 해당 이메일의 해시만 지정해 제거한다.
- [ ] 삭제 후 같은 테스트를 재실행해 대상 사용자·세션·실패 행은 0건이고, 무관 계정·실패 행은 그대로인지 확인한다.

#### Task 2 — 로그인 세션으로 보호되는 질문 API

**파일:** `backend/main.py`, `tests/api/test_question.py`, 필요 시 `backend/BACKEND.md`.

### 1단계 인증 테이블 보호안 — 테스트 프로젝트 적용 및 권한 검증

2026-11-04 읽기 전용 확인: 세 테이블 소유자는 `postgres`, RLS 정책은 없고 RLS는 비활성이다. `anon`과 `authenticated`는 세 테이블 SELECT 실효 권한과 `users_id_seq` USAGE 권한이 있다. 현재 `.env` 백엔드 접속 역할은 `postgres`이며 RLS 우회 속성이 있다. 이는 동작 가능성의 근거이지 최소 권한 설계의 완료가 아니다.

Supabase 보안 advisor의 RLS 제안을 포함한 다음 변경안은 **테스트 프로젝트의 세 인증 테이블과 그 ID 시퀀스만** 대상으로 한다. 사용자 승인으로 `restrict_auth_tables_public_access` 마이그레이션을 적용했다. 공개 역할의 직접 접근을 막고 별도 RLS 정책은 만들지 않는다. 공개 역할의 DB SELECT 거부와 실효 권한, 백엔드 역할의 트랜잭션 CRUD 롤백, advisor를 확인했다. HTTP Data API와 실제 로그인은 미검증이다. `postgres` 역할에 과도한 권한이 있으므로 후속으로 전용 최소 권한 역할을 별도 검토한다.

```sql
BEGIN;
REVOKE ALL PRIVILEGES ON TABLE public.users, public.auth_sessions, public.auth_login_attempts FROM PUBLIC, anon, authenticated;
REVOKE ALL PRIVILEGES ON SEQUENCE public.users_id_seq FROM PUBLIC, anon, authenticated;
ALTER TABLE public.users ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.auth_sessions ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.auth_login_attempts ENABLE ROW LEVEL SECURITY;
COMMIT;
```

실패 시 무조건 이전 공개 권한을 복구하지 않는다. 트랜잭션 실패 여부와 현재 권한을 확인하고 보안 경계를 유지하는 수정안을 기록한다. 기존 권한 회복이 필요한 경우 영향 범위와 담당자를 확인한다. pgvector와 나머지 테이블에는 실행하지 않는다.

**정책 검토 상태:** 사용자는 A안(DB 저장 암호화와 접근 통제)을 선택 방향으로 제시했다. 앱 계층 이메일 암호화/복호화는 도입하지 않으며, DB 조회 권한자에게 평문 이메일이 보일 수 있는 방향이다. 팀 합의와 실제 DB 설정 검증은 남아 있다. 실패 기록 보관, 계정/백업 삭제 기준, 실제 개인정보 사용 시점은 별도 결정 사항이다.
